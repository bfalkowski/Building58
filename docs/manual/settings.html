Settings

Every environment variable the relay, its scripts and the hook read, with its default. Set them when you start the relay, for example RELAY_WIP_LIMIT=4 npm run office.

The limits and timings are also in Settings on the room page, on its tabs, as The Settings window, by tab says (relay/config.js, GET and POST /settings): RELAY_WIP_LIMIT, RELAY_READY_LIMIT, RELAY_UPDATE_HOLD_MS, RELAY_UPDATE_WAIT_MS, RELAY_UPDATE_FORCED_MS, RELAY_LEAD_CHECK_MS, RELAY_LEAD_STOPS, RELAY_LEAD_STOP_LIMIT, RELAY_REVIEW_POLL_SECONDS, RELAY_PIPELINE_POLL_SECONDS, RELAY_MAIN_CI_POLL_SECONDS, RELAY_PIPELINE_NO_CHECKS_MS, RELAY_REVIEW_RETRY_MS, RELAY_REVIEW_GRACE_MS, the RELAY_AUTOPILOT_* limits and timings, RELAY_CHAT_KEEP, RELAY_CHAT_POLL_SECONDS, RELAY_MAIN_POLL_SECONDS, RELAY_CHAT_RETRY_MS, RELAY_HUDDLE_*, RELAY_STALL_MS, RELAY_MANAGER_* limits, RELAY_PR_WATCH_SECONDS, RELAY_PR_WATCH_WAIT_MS, RELAY_COO_GRACE_MS, RELAY_SECURITY_GRACE_MS, RELAY_PM_TALK_MINUTES, RELAY_PM_TRUST, RELAY_PM_CHECK_MS and RELAY_PM_SORT_HOURS. Three have no variable and are set only there: automatic reviews per PR (3), and Autopilot's review rounds (2) and merges a day (10). Each is read when it is used, so a change applies at once, with no restart. A value set on the page wins over its variable, and stays through a restart, in ~/.office-world/settings.json (RELAY_SETTINGS_FILE). Reset goes back to the variable, or the default. The page shows the timings in seconds or minutes, where the variable may be in milliseconds.

The rest are read only at startup, and a running relay keeps the ones it started with: the port and the key, which the page needs to connect; where state is kept; whether the terminal is on and which claude runs, which a page must not be able to change; the ticket store; the webhook; and the supervisor's own variables.

The Settings window, by tab

The Settings window on the room page has seven tabs, down its left side. On a narrow window they become one menu. The search box at the top looks in the label and help text of every setting on every tab, and opens the first tab with a match. A setting that differs from its default shows changed, and its tab shows how many it has. The tab you used last is kept in this browser. Each setting has its tab in relay/config.js, and GET /settings says which. The tables show the default, and the variable where there is one. A value set in Settings wins over its variable.

The relay

VariableDefaultMeaning
RELAY_KEYrandom, printed at startThe key every call to /channels/... must send. The supervisor hands it to the relay it starts, and both take it out of their own environments, so nothing they run is given it: not a session, not git or gh, not the git a rollback runs, and not the session host.
PORT8787, or the world's portPort to listen on. With RELAY_WORLD, the default is the port in that world's world.json.
RELAY_REMOTEoff1 turns on remote mode: a request for the public address must carry a Cloudflare Access sign-in of the owner, with MFA. Needs the four variables below, or the relay does not start. Keep them in .env, not in the repo.
RELAY_REMOTE_URLnoneThe room's public address, such as https://room.example.com. It must be https. A request whose Host is its host is remote, and an Origin must be this address.
RELAY_ACCESS_TEAMnoneThe Access team domain, such as myteam.cloudflareaccess.com. It gives the issuer and where the public keys are.
RELAY_ACCESS_AUDnoneThe application's audience tag, from the Access application's overview.
RELAY_ACCESS_EMAILnoneThe owner's email. No other email gets in.
RELAY_ACCESS_MFAamrHow remote mode knows the owner used MFA. amr: the token's amr list must hold mfa, which the owner's identity provider sets. cloudflare: the relay does not read amr, and MFA is left to the Access application's own MFA setting. Use it when the identity provider does not send amr, as Google does not. Then a wrong MFA setting in Access is not caught by the relay: the other checks still are. Empty means amr, and any other value stops the relay.
RELAY_REMOTE_FULLoff1 lets the owner use the whole room through the tunnel: a request that passed remote mode counts as the room page on this computer for the local-only rule, so the Claude Code panel, sessions, the Floor, the Board, Tasks and Update answer it. The owner's sign-in then guards a panel that can run any command on this computer. 0 or unset: remote mode lets the owner watch only. Any other value stops the relay.
RELAY_ACCESS_CERTS_URLthe team's /cdn-cgi/access/certsWhere the relay fetches the team's keys. Only tests set it. Whoever can set it can choose the keys, so leave it unset.
RELAY_WORLDnone: every worldA world's folder. The relay serves that world alone, and loads the room's parts only if its world.json says "sessions": true. npm run world -- <folder> sets it, and npm run office sets it to office. See One relay per world.
HOST127.0.0.1Address to listen on. A tunnel connects locally, so this can stay as it is.
RELAY_ROOTthe repo folderWhere the page files are served from. See what the relay serves. Files under relay/ are never served.
RELAY_TERMINALoff1 turns on the Claude Code panel, the Board, Tasks, checkouts and Update. npm run office sets it on a relay it starts, but not on one already running. It only answers the room page on this computer. See the local-only rule.
RELAY_UPDATE_DIRthe relay's folderWhere Update pulls, and where a rollback checks out the last good commit.
RELAY_ROLLBACKoff1 checks each relay the supervisor starts, and goes back to the last commit that passed when the relay fails after an Update. Read once, when the supervisor starts. See When the new relay fails.
RELAY_ROLLBACK_SECONDS60How long a new relay has to pass that check. At least 5.
RELAY_UPDATE_STEPS20While RELAY_ROLLBACK=1, the most merges one Update takes, one at a time. The rest wait for the next. From 1 to 100. See One merge at a time.
RELAY_RESUME10 starts the relay with nobody: it brings back no session from the last run, ends any still running in the session host, and starts no Lead. See Bringing a session back.
RELAY_WORKER, RELAY_SUPERVISED, RELAY_KEY_RANDOMset by the supervisorTell the relay it runs under relay/supervisor.js, and whether the key was made up. Not for you to set. Sessions do not get them.
RELAY_HOST_SOCKETset by the supervisorThe socket of the session host, which runs the sessions. Not for you to set. Sessions do not get it.

Files on disk

The relay keeps its state in one folder, the state folder. RELAY_STATE_DIR sets it, and each file's own variable below still wins over it. The Lead's handoff notes, the GitHub store's key and the settings from the page are there too. A second room on the same computer needs only its own port and its own state folder (see A second room).

One relay owns each of the tasks, checkouts, sessions, reviews, deliveries and Lead files at a time: a second one using it keeps that state in memory only, and says so. A relay claims a file with a .lock beside it that holds its pid. A relay that was killed leaves its .lock files, and after a reboot, or in a new container, which numbers its processes from 1 again, that pid can belong to another process. So a claim counts only while its pid is still a relay/server.js process, and the next relay takes the file.

Standing rules

A standing rule is something you want to hold for a while, such as "do not touch the payments folder until Friday". Keep them in Settings, under Standing rules: type the rule, why, and the day it ends (or leave the day empty for until you remove it), then press Add rule. Remove deletes one. The room keeps 10, each with up to 200 characters of rule and 200 of reason. The list is kept through a restart in ~/.office-world/rules.json (RELAY_RULES_FILE).

The brief the relay types for each new Dev, reviewer, Lead and PM ends with the rules in force, each with its reason and end date. The brief says that a standing rule never overrides CLAUDE.md or the constitution. A rule holds through its end date. After that day it leaves new briefs by itself, and the list shows it as ended until you remove it. A new rule reaches sessions that start after you add it, not sessions already running. A session can read the list with ticket.js rules, and cannot add, change or remove a rule (/rules in the routes).

Models and skills for each role

In Settings, on the Roles tab, each role has a model and a list of skills: the Lead, Devs, reviewers, the PM, the COO and the security officer. They have no variables, and are kept with the other page values in ~/.office-world/settings.json. Reset goes back to the default. The code is in relay/skills.js.

It says it once after the relay starts, when a session with a role starts, and again only when the missing list changes. Sessions carry on without the missing skills.

Given to sessions

Sessions the room starts get OFFICE_TERMINAL_ID, OFFICE_TICKET_TOKEN and OFFICE_TICKET_URL, which relay/ticket.js reads. They also get OFFICE_CHANNEL, set to the channel of the page that started them, the same value in OFFICE_PANEL_CHANNEL, which tells office-hook.js --install the panel set it, and OFFICE_HOOK_URL, the address of that relay's channel (http://127.0.0.1:<port>/channels/<channel>/commands). With OFFICE_HOOK_URL and the token, the hook reports to the relay that started the session, even when the hooks in ~/.claude/settings.json name another relay, key or channel. The token sends only hooks about its own session, and the relay seats them at that session's desk. RELAY_KEY, OFFICE_RELAY_KEY, RELAY_TERMINAL and the supervisor's variables are taken out of what they inherit.

They also get NODE_OPTIONS, with what you set there kept and the test slot gate added (relay/test/slot-gate.js). So the test files of every node --test run in a session, in any repo, Exhibit too, share the test slots of Building58's own npm test: one slot for each core of the computer, or TEST_SLOTS, set where you start the relay. Each test file takes a slot before it loads and holds it until it ends, and a file that must wait says # waiting for a test slot once. When a slot frees, the run that started first goes on. A test run that a test file starts itself does not take a slot, so it never waits behind its own parent. Other node processes pass through at once. NODE_OPTIONS names a small file, slot-gate.js, in the room's state folder, which loads the gate only if it is still there, so node still starts in a session that outlives the code, as after a rollback. With TEST_SLOTS=0 the relay adds nothing. A session started before you restart the relay with this change does not have the gate.
