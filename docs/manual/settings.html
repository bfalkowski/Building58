Settings

Every environment variable the relay, its scripts and the hook read, with its default. Set them when you start the relay, for example RELAY_WIP_LIMIT=4 npm run office.

The limits and timings are also in Settings on the room page, under Limits and timings (relay/config.js, GET and POST /settings): RELAY_WIP_LIMIT, RELAY_READY_LIMIT, RELAY_LEAD_CHECK_MS, RELAY_LEAD_STOPS, RELAY_LEAD_STOP_LIMIT, RELAY_REVIEW_POLL_SECONDS, RELAY_PIPELINE_POLL_SECONDS, RELAY_PIPELINE_NO_CHECKS_MS, RELAY_REVIEW_RETRY_MS, RELAY_REVIEW_GRACE_MS, the RELAY_AUTOPILOT_* limits and timings, RELAY_CHAT_KEEP, RELAY_CHAT_POLL_SECONDS, RELAY_MAIN_POLL_SECONDS, RELAY_CHAT_RETRY_MS, RELAY_HUDDLE_*, RELAY_STALL_MS, RELAY_PR_WATCH_SECONDS, RELAY_PR_WATCH_WAIT_MS, RELAY_COO_GRACE_MS, RELAY_SECURITY_GRACE_MS and RELAY_PM_TALK_MINUTES. Three have no variable and are set only there: automatic reviews per PR (3), and Autopilot's review rounds (2) and merges a day (10). Each is read when it is used, so a change applies at once, with no restart. A value set on the page wins over its variable, and stays through a restart, in ~/.office-world/settings.json (RELAY_SETTINGS_FILE). Reset goes back to the variable, or the default. The page shows the timings in seconds or minutes, where the variable may be in milliseconds.

The rest are read only at startup, and a running relay keeps the ones it started with: the port and the key, which the page needs to connect; where state is kept; whether the terminal is on and which claude runs, which a page must not be able to change; the ticket store; the webhook; and the supervisor's own variables.

Files on disk

The relay keeps its state in one folder, the state folder. RELAY_STATE_DIR sets it, and each file's own variable below still wins over it. The Lead's handoff notes, the GitHub store's key and the settings from the page are there too. A second room on the same computer needs only its own port and its own state folder (see A second room).

One relay owns each of the tasks, checkouts, sessions, reviews, deliveries and Lead files at a time: a second one using it keeps that state in memory only, and says so.

The PM's notes are in pm-notes/ in the state folder, one file per repo (see The PM notes), and the relay names the file in each PM's brief.

Models and skills for each role

In Settings, under Models and skills, each role has a model and a list of skills: the Lead, Devs, reviewers, the PM, the COO and the security officer. They have no variables, and are kept with the other page values in ~/.office-world/settings.json. Reset goes back to the default. The code is in relay/skills.js.

SettingDefaultMeaning
ModelemptyThe model a new session for that role starts on: the relay adds --model and the value to its claude command. Empty adds nothing, so the session runs on your own default. The box suggests opus, sonnet and haiku, and takes a full model id too. A value is letters, digits, dots, dashes and brackets, up to 64, and cannot start with a dash; the relay refuses anything else. Only a new session gets it. A session brought back with --resume keeps the model it had, so a /model switch you made by hand stays through a restart.
SkillsSee belowSkills the role's brief names, by their plugin name, split by commas or spaces, up to 12. The brief gets one paragraph: use these skills where they fit, carry on without one that cannot be called or read, and the repo's rules win where a skill and CLAUDE.md or the constitution differ. It names only the skills installed on this computer. A skill a session can call is named for the Skill tool. A skill only a person can run (its SKILL.md has disable-model-invocation: true, as most pstack skills do) is named with the full path of its SKILL.md, and the session is told to read that file and follow it where it fits. The path goes only into the brief, never into #office or Settings. Empty: no paragraph. Next to each list, Settings says which skills are not found, and which are read from their file.

Which role a session starts as: a task's worker is a Dev, a session for a PR review is a reviewer, and Ask the PM and the COO's report start the PM and the COO. The Lead's model applies only when the relay itself starts the Lead as a new session: when it starts a new Lead because none came back (When the relay starts), or after a stop, when it brings back the Lead and the Lead had no conversation yet (it was made the Lead and its brief had not gone in, or it was between /clear and its next prompt). A session you make the Lead is already running, so it keeps the model it started on. Bring back resumes the Lead's conversation, so it keeps its model too. A plain session, with no role, never gets --model.

The default skills: the Lead pstack:recall; Devs mattpocock-skills:tdd, mattpocock-skills:diagnosing-bugs, mattpocock-skills:codebase-design, pstack:blast-radius, pstack:principle-prove-it-works and mattpocock-skills:pr; reviewers mattpocock-skills:code-review and pstack:blast-radius; the PM pstack:sharpen and mattpocock-skills:writing-for-agents; the COO pstack:principle-explain-the-number. The Dev's brief says what three of them are for: tdd for new behavior or a bug a test can catch, diagnosing-bugs for a bug, and codebase-design for a change of structure.

What is installed comes from Claude Code's own files, which the relay reads and never writes: ~/.claude/plugins/installed_plugins.json for each plugin and its folder, and enabledPlugins in ~/.claude/settings.json, where a plugin set to false does not count. A plugin's skills are the folders under its skills folder that hold a SKILL.md. CLAUDE_CONFIG_DIR moves ~/.claude, as it does for Claude Code. The relay reads them again only when one of those two files changes. When a skill on any list is not installed, #office on the chat board says which, and the commands that install its plugin, such as /plugin install mattpocock-skills@claude-plugins-official. It says it once after the relay starts, when a session with a role starts, and again only when the missing list changes. Sessions carry on without the missing skills.

Given to sessions

Sessions the room starts get OFFICE_TERMINAL_ID, OFFICE_TICKET_TOKEN and OFFICE_TICKET_URL, which relay/ticket.js reads. They also get OFFICE_CHANNEL, set to the channel of the page that started them, the same value in OFFICE_PANEL_CHANNEL, which tells office-hook.js --install the panel set it, and OFFICE_HOOK_URL, the address of that relay's channel (http://127.0.0.1:<port>/channels/<channel>/commands). With OFFICE_HOOK_URL and the token, the hook reports to the relay that started the session, even when the hooks in ~/.claude/settings.json name another relay, key or channel. The token sends only hooks about its own session, and the relay seats them at that session's desk. RELAY_KEY, OFFICE_RELAY_KEY, RELAY_TERMINAL and the supervisor's variables are taken out of what they inherit.

Settings kept in files

  • office/roster.js says who works here and how they look. The first startWith people (three) are always in the room, and the rest come in for a session and leave when it ends. The people's skills are only used by the work action (see the room's API). The manager's visits are set there too, as manager.everyMinutes. Take it out and the manager only comes when sent. The relay reads the file too, named by roster in office/world.json, to pick the desk each session sits at and the name it shows (Which person gets it). Its names are the pool of names, one list for each desk kind: keep each name one word, and apart from the desks' own names. It reads it when it starts, so restart the relay after you add, remove or rename someone.
  • office/radio.js: SOUR, WOW and FLUTTER at the top set how far out of tune the radio is.
  • In the browser. The Org chart's next arrangement, who had which session, for a day, and Send each status report to the Lead, the switch in Settings under Huddle (on until you turn it off; see Telling the Lead). The review switches are the relay's, in RELAY_REVIEWS_FILE.
