The relay API and routes

The relay is a small server between callers and the world pages, such as the room. This page has its calls, its errors, its events, the room's API, the room's routes, and the scripts that drive it.

What the relay is

Each world runs in a browser page, and nothing outside the browser can call into a page directly. The relay (relay/server.js, Node 18 or later, no dependencies) sits in the middle. Callers such as curl, a script or an agent send commands to the relay over HTTP. The relay passes each command to the page, waits for the result and sends it back. The page also sends every event to the relay, where callers can read them or have them posted to a webhook. shared/relay.js connects a world page to the relay when it is opened with ?channel=, and uses only window.run.

The relay also serves the page, so the world and the relay share one address. That avoids the browser's cross-origin and local-network blocks, and once the relay is behind a tunnel the same URL works for any caller and any browser. It serves files from the repo folder (RELAY_ROOT): the room at /office/, any other world at its folder's name, this manual at /docs/manual/, and the root links to the room. It does not serve dot folders such as .git, or any folder named relay or node_modules, in any case, so /RELAY/server.js gets 404 too. It refuses any path with a character that is not ASCII, since macOS reads some of them as plain letters. A path with a malformed escape, such as /%E0%A4%A, gets 404. A path that starts with two slashes, such as // or //office/, gets 404 for any method. An unknown route under /channels/ gets 404 with not_found, and a channel name with a malformed escape, such as /channels/%E0%A4%A/tickets, gets 400 with the relay key with bad_channel.

Worlds. The relay does not know any world by name. A world is a folder in RELAY_ROOT with a world.json: name and channel make its link, port is where its own relay listens, and "sessions": true says its page runs Claude Code sessions, the Board and Autopilot. For example, { "name": "the office", "channel": "office", "port": 8787, "sessions": true }. A folder with no world.json, or one that is not valid JSON, is not a world, but with no RELAY_WORLD its files are still served. A world's own scripts live in its folder. A world can live in a repo of its own and be linked into RELAY_ROOT as a folder link: the relay serves it like any other folder. The rule is in CLAUDE.md and article 13 of the constitution, and relay/test/worlds-apart.test.js fails if code in relay/, office/ or shared/ names another world.

One relay per world. RELAY_KEY=a-key npm run world -- <folder> (relay/world.js) starts a relay for that world alone, on the port in its world.json. It sets RELAY_WORLD, which you can also set yourself, and PORT to the world's port unless you set it. RELAY_WORLD is one folder name: a trailing slash, as tab completion gives, is dropped, and anything else, such as a/b or /, stops the relay with the reason. Give each world its own key. The rollback check is for the room's relay: it looks for the room page and its sessions, so leave RELAY_ROLLBACK off for another world. Such a relay:

  • prints one link, its world's, and sends its root (/) to its world's folder;
  • serves only its world's folder, shared/, docs/ and the files at the top of the repo, such as README.md. Another world's folder gets 404, so a link into another world works only on that world's relay;
  • for a world without "sessions": true, never loads the room's parts: no sessions, tasks, tickets, Board, chat board, reviews or Autopilot, no polls to GitHub, and no files in the state folder. Their routes get 404. Commands, results and events work as for any world;
  • keeps running when another world's relay restarts or stops, and its key opens nothing in another world.

npm run office starts the room's relay this way, with RELAY_WORLD=office. npm run relay, with no RELAY_WORLD, still serves every world from one relay with the room's parts, on port 8787. /health says which world a relay serves, as world, or null for every world.

The page

The page connects to a relay only when its address has a channel:

ParameterMeaning
channelThe channel to join: 1 to 64 letters, numbers, dashes or underscores.
keyThe relay key.
relayThe relay's address, if it is not the server the page came from.
othersA world can read parameters of its own, such as the room's below.
timeThe room only: day, evening or night, the same as picking the light.
holidayThe room only: a holiday to show now (newyear, easter, july4, halloween, thanksgiving or christmas), the same as picking it under Holiday, or off for no decorations on that page. See Holidays.
lookThe room only: baked for the room's light baked in Blender, for each time of day, with fx=off to leave out its effects. See The baked look.

The world only runs while its page is on screen. Each page tells the relay when its tab is hidden or shown, and the relay log says so. If more than one page joins the same channel, commands go to the newest page that is on screen, or to the newest page if none is. A page on this computer always comes first: a page that came through a tunnel (its stream had a Cf- header, or the remote mode public address) gets commands only when no page on this computer is open, so a phone never takes the room's hooks from the laptop's page. A command sent to a hidden page waits and then times out, and the reply says that the tab is hidden (pageHidden: true). It is simplest to use a different channel for each page.

Calls

All calls to /channels/... need the key, as Authorization: Bearer <key> or ?key=<key>, or the cookie the room page sets (The relay key and the room page). Bodies are JSON.

The same calls and the room's routes are in docs/openapi.json, an OpenAPI 3.1 document that the relay serves at /docs/openapi.json. It is the API at version 2.5.1. npm run openapi builds it from the tables on this page: each row's Name is its operation's id, and its summary, and each row is one operation, with a description of only what that operation does. The operations are grouped by tags with readable names, such as Tickets, Sessions and Needs you, each with a line about it, from the first part of the path. relay/openapi.js keeps the list, and a route with no tag there stops the build. Each operation lists, in x-tokens and in its description, the session tokens that reach it, worked out from the rule the relay keeps (relay/token-routes.js). The two streams are text/event-stream.

The core resources and requests have schemas, in relay/api-schemas.js and in the document: a ticket, a task, a session, a row of the Floor, an event, a command and a reviewer's verdict. Each request schema has an example, which npm test checks against the schema. Before a route reads a request with a schema (createTicket, editTicket, createTask, moveTask, sendCommand and postVerdict), the relay checks the JSON type of each field it knows, and answers 400 with bad_type and the field's name when one is wrong. Fields it does not know pass through. The route then checks the values, such as the length of a title or the list of priorities, with its own error codes, as before. npm test fails when docs/openapi.json is out of date, a route in it does not answer, a real answer does not fit its schema, a request that breaks its schema is not refused, or the document changed since main without a new version. A change to the API takes a new version, as the constitution says in article 15.

For example, with the room open on channel office, on its own relay (npm run office, port 8787):

curl -s -X POST http://localhost:8787/channels/office/commands \
  -H "Authorization: Bearer pick-a-long-random-key" \
  -d '{"action": "say", "who": "marcus", "text": "Hello", "source": "curl"}'

Send a command

POST /channels/{channel}/commands. The body is a command, the same as run.do() takes (see the world's own API, such as the room's API), plus fields for the relay:

FieldDefaultMeaning
actionrequiredOne of the world's actions. The room's are below.
source"relay"Your name, shown on every event the command causes. For a script, something like "script:standup".
waittrueWait for the result. With false, the reply is 202 with an id to poll.
timeout30Seconds to wait, from 1 to 120.
 
{ "action": "say", "who": "marcus", "text": "Hello", "source": "script:standup" }

The reply is the world's result with the command's id, channel and action added:

{ "id": "ba29db55-d4bf-40e1-a99b-9ba42c0652b6", "channel": "office", "action": "say",
  "ok": true, "who": "marcus" }

When the world refuses a command, the reply is still 200, with ok: false, an error and a message (each world lists its own errors):

{ "id": "30b74e34-...", "channel": "office", "action": "dance",
  "ok": false, "error": "unknown_action", "message": "Unknown action \"dance\". Actions: ready, state, roster, ..." }

So a caller checks ok to see whether the world did it, and the HTTP status to see whether the relay could deliver it:

StatuserrorMeaning
200The world answered. Check ok.
202Accepted with wait: false. Poll /commands/{id}.
400bad_command, bad_request, bad_channel, bad_typeNo action, the body is not JSON, a bad channel name, or a field of the wrong JSON type in a request with a schema, such as a number for a title. The message names the field.
401unauthorizedMissing or wrong key. The message says which.
403local_only, and others such as not_allowed or lead_onlyA room route asked from anywhere but the room page on this computer, or a token asking for what it cannot do. See the room's routes.
409such as wip_limit, lead_limit, bad_moveA room route refused a move or a start, and the message says why. A ticket store that refuses a change, such as a GitHub issue with a note the relay's key did not sign, answers 409 and store_refused with the store's own message. A store that fails otherwise answers 502 and store.
404not_found, unknown_commandNo such route or command id.
413bad_requestThe body is over 256 KB.
503no_pageNo page is connected to the channel.
504timeoutThe page did not answer in time. The command may still finish; poll its id. pageHidden: true means the page's tab is hidden, so its world is paused.

Some commands take time in the world, such as wait, which takes as long as you ask. Set the caller's own HTTP timeout above the longest command you send.

Poll a command

GET /channels/{channel}/commands/{id} returns { "status": "pending" } or { "status": "done", ...the same reply as above }. The last 500 commands per channel are kept.

Read events

GET /channels/{channel}/events?since=0&types=result,worker.assigned&limit=200

{ "ok": true, "channel": "office", "lastEventSeq": 42,
  "events": [ { "rseq": 41, "type": "worker.assigned", "who": "marcus", "label": "T-17", "source": "relay", ... } ] }

rseq is the relay's own sequence number for the channel. Pass the last one you saw as since to get only newer events. Every event also keeps its fields from the page. The last 2,000 events per channel are kept. The relay keeps them in memory, so a restart clears them.

Webhook

With RELAY_WEBHOOK_URL set, the relay posts batches of events as they arrive, but only the types in RELAY_WEBHOOK_TYPES. Its default is result, run.started, run.live, run.off, thing.added, dale.said, dale.moved and phone.rang, so of the room's events only result is sent unless you name more. With worker.assigned named:

{ "channel": "office", "events": [ { "type": "worker.assigned", "who": "marcus", ... }, { "type": "result", "action": "say", ... } ] }

RELAY_WEBHOOK_AUTH is sent as the Authorization header, and RELAY_WEBHOOK_TYPES, a list split by commas, picks which event types are sent. A post that cannot reach the address is logged. A post the address answers with an error is not. Neither is retried.

Events: office.started, office.live, time, worker.assigned, worker.finished, worker.doing, lead.waiting, lead.unblocked, manager.arrived, manager.left, lead.visit, party.started, party.ending (the candles go out), party.ended, hook, and action and result for every action except hook, sessions and tasks. Those three send a result only when they fail.

In the browser console, run.view('desks') moves the camera (home, desks, lead, coffee, lounge, board, office), run.focus('marcus') follows someone, run.time('night') changes the light, and run.holiday('christmas') shows a holiday's decorations ('auto' goes back to the date, 'off' and 'on' set the switch this browser keeps). run.state().holiday says what is up and which holiday is next.

The room's routes

These are under /channels/{channel} and answer only the room page on this computer (see the local-only rule), while RELAY_TERMINAL=1. /pr-watch, /ready, /old-relays, /games, /rounds and /play answer without it too. They take the relay key, or a session's token as described below.

It also has kinds (the kinds a ticket can have, see Kind), labels (the labels tickets have, A to Z, see Labels), wipLimit, leadStarts (the number you let the Lead start tickets up to, or 0) and leadStartsLeft. A ticket has approvedBy (you or Lead) once it is put in Ready. The room page gets the same list as a tickets event on its GET /stream when it opens the stream with board=1, with people, who sits on each ticket, and without the time each pipeline was checked. The stream's hello says whether it will (tickets). It is sent once as the stream opens, then only when it changes, and only to the room page on this computer.

When the same repo already has an open ticket with the same title, the answer is that ticket, with duplicate: true, and nothing new is filed. For a session's token, a rejected ticket counts too.

For the PM and the Lead, a ticket you rejected counts too, as in filing. Only the fields that differ are written: the answer's edited lists them, and has unchanged when none do. What a session's token reaches

Each session the room starts gets OFFICE_TICKET_TOKEN, sent as X-Office-Token. Tokens reach nothing but this:

  • Any session's token can GET and POST /tickets, except the COO's, which can only GET it.
  • Any session's token can POST /commands, but only {"action": "hook"} with an event about its own session: the hook sends that way to OFFICE_HOOK_URL. The relay sets the event's terminal to that session's desk. A SessionStart may carry a new session id, after /clear. Anything else gets 403.
  • Any session's token can POST /terminals/context, but only for the conversation its session is in now: its status line says how full its context is (How tired the Lead is).
  • Any session's token but the COO's and the security officer's can GET /chat and /chat/{name}, and POST /chat/{name}. A post that mentions a session is typed into it, and those two only propose. Their tokens can list tickets but not file them.
  • Any session's token can GET /rules, the standing rules (ticket.js rules). POST /rules, /rules/{id} and /rules/{id}/remove get 403 person_only: only the person adds, changes or removes a rule.
  • A reviewer's token can also POST /autopilot/verdict, for the PR it reviews. No token reaches /autopilot itself.
  • The Lead's token can also POST /autopilot/fix with {"task"}, a task id, ticket id or PR link, while Let the Lead merge is on. With the switch off it gets 403. Any other session's token gets 401. The person's key reaches it too: it is Fix it on Needs you. It answers 404 with not_a_task when no task matches, and 409 with no_merge_verdict when the latest posted verdict on its PR does not say merge. See The push hold.
  • The Lead's token can also GET /floor, and POST /ready to mark a PR ready to merge.
  • The token of a session you made the Lead and let move the board can also POST /tasks/{id}/move and /tickets/{id}/move, and GET /tasks, which then shows only each task's id, state, title, branch and PR. With Let the Lead stop sessions on (RELAY_LEAD_STOPS=1 sets its default) it can also POST /floor/stop. While Autopilot is on, a move is refused with 403 and autopilot unless it takes a task, or a ticket with no task, to Done once the relay has seen its PR merge. See The Lead under Autopilot.
  • The COO's token can also GET /officers/coo/measures and POST /officers/coo/report.
  • The Lead's token can also POST /reviews/lead with {"pr": ...}. A session that is no longer the Lead gets 401. The Lead gets 403 while Let the Lead start reviews and Autopilot are both off, 400 for a link that is not a PR, 404 with not_a_task for a PR that is not a task's, and 409 with reviewing, full or limit for a PR a reviewer is on, no free desk, or a PR past its reviews. See The Lead starts a review. The person's key gets 403 here: the page has Get a review.
  • The security officer's token can also GET /officers/security/measures and POST /officers/security/report.
  • The token of a session you made the Lead and let start tickets can also POST /tickets/{id}/start, within the limits in The Lead starts tickets, and never while Autopilot is on. While a round of a game runs, it gets 409 with held (see Games).
  • A seat's token, in a round of a game, reaches only POST /play, its own hooks on /commands and its status line on /terminals/context. Everything else, tickets and the chat board included, gets 403.
  • The PM's token can also send a priority in POST /tickets/{id}/edit, and POST /tickets/{id}/order, but only while Let the PM set the order is on, only for a ticket in Triage or Ready, and only for the PM that started last on the channel. Otherwise it gets 403. The relay checks the switch again when the request's turn comes, so a request that was waiting when you turned the switch off is refused too. A ticket set this way has orderedBy PM, and one you set has you, with orderedWhat priority or place.
  • Any session's token but the COO's and the security officer's can POST /tickets/{id}/note, for a ticket at any status. A note changes nothing else on the ticket.
  • The PM's and the Lead's tokens can also POST /tickets/{id}/propose, for a ticket in Triage or Ready. The proposal waits for the person, and no session's token can answer it on /tickets/{id}/proposal.
  • The PM's and the Lead's tokens can also POST /tickets/{id}/edit, for a ticket in Triage or Ready. A priority in it needs the PM's or the Lead's switch, below, or the whole edit gets 403. Any other field, such as kind or base, gets 403. A ticket that is starting, started, done or rejected gets 403. A new title or body on a Ready ticket you approved takes your approval back, and the answer has approvalTaken.
  • The Lead's token can also send a priority in POST /tickets/{id}/edit, and POST /tickets/{id}/order, but only while Let the Lead set priority is on, only for a ticket in Triage or Ready, and only while the session is still the Lead. It does not need Let the Lead move the board. Otherwise it gets 403. The relay checks the switch again when the request's turn comes. A ticket set this way has orderedBy Lead.

Other routes answer a token with 401. /tickets/{id}/order answers every other token with 403, and so do /tickets/{id}/edit and /tickets/{id}/propose for every token but the PM's and the Lead's. The PM's token gets 403 on /tickets/{id}/move and /start. Each operation in docs/openapi.json lists the tokens that reach it, from the same rule the relay keeps (relay/token-routes.js).

Games

The room can act out a game from another repo for one round, from the Games panel or these routes. The room does not change, only the roles of the sessions in it. Set GAMES_REPO to a folder of games. A game is a folder in it with a game.json: {"name", "version", "api": 1, "entry", "players": {"min", "max"}, "needs"}, and if it likes "about", what a round is in plain words, and "metrics", {"name": "what it means"} for the numbers in its score. This relay can meet the needs privateBriefs, ask and files. No code in relay/, office/ or shared/ names a game, and relay/test/games.test.js checks that when GAMES_REPO is set.

A round runs the game's entry with node, in the game's folder, as its own process, without the relay's key. They talk in JSON lines. The relay sends hello, setup (seed, settings, seats), action (id, seat, kind, args), finish and abort. The game sends hello, brief (seat, text), ready, answer (id, text), spend (usd) and done (score, reveal).

  • Seats. Each seat (S1, S2 and on) is a fresh session at a free desk, in a new folder that is not a copy of a repo, with no task. Every seat folder sits under one parent, ~/.office-world/seats/<round>/<seat>, and goes when its seat ends. Its brief is typed as its first prompt and kept nowhere else: not in a file, the relay's log, a title or any route but the seat's own steps. Those go only to your room page, which can already see the brief on the seat's screen. A seat's hooks reach the room without their words. The relay has no field for a role. Only the game knows who is what.
  • Playing. A seat runs node "$OFFICE_PLAY" ask "a question", or another kind its brief names, and gets the game's answer. Its folder is empty, so the relay gives it the full path of relay/play.js as OFFICE_PLAY. The game routes answer only the room page and the sessions on this computer, like every room route.
  • Watching. A round is watch: "all" (the default): you can open any seat's screen. Or "none", for when you play too: a seat's screen is refused with 403 until the round ends. Either way a seat is read-only to you: typing into it gets 403. The one exception is Claude Code's question about trusting the seat's folder. Nothing is typed into a seat while that question is up, so GET /rounds/current shows that seat with waiting: "trust", and you may answer it. Claude Code's first choice there is No, so Enter alone ends the seat: the answer is Down, then Enter, as the Games panel sends it. You can also trust ~/.office-world/seats once in Claude Code, if it honors a parent folder's trust for the folders under it. That is not checked yet.
  • The rest of the room. While a round runs, the Lead and Autopilot start no new tickets. Work already running goes on.
  • The end. Finish shows the game's score and reveal, and a second Finish while the first waits gets the same answer. Stop ends it with no score. A game that exits, sends a line that is not JSON, or does not answer for RELAY_GAME_TIMEOUT_MS (30 seconds) ends its own round, and so does a round that reaches its spend cap. Then every seat is stopped and its folder removed. The relay keeps only each round's id, game, time, spend and score while it runs, and for each seat its folder and session id, so you can still read its steps.
  • Steps and spend. Claude Code keeps each session's transcript in ~/.claude/projects/<the folder, each sign a dash>/<session id>.jsonl, and it stays after the seat's folder goes. relay/seat-steps.js reads it: the steps for GET .../steps, and the tokens of each request once, priced per model at Claude API list prices, with cache writes at 1.25 times input for 5 minutes and 2 times for 1 hour. Claude Haiku 5.5 has a higher price for a request whose prompt is over 100K tokens, and the relay counts that too. Its cache reads are counted at a tenth of input, since no list price is given for them. While a round runs, the relay reads each seat's transcript again every RELAY_SEAT_SPEND_MS (5 seconds) when it has grown, adds what the game reports, and stops the round at its spend cap. Text in a <system-reminder> block, which Claude Code adds with your global rules and account, never comes out in a step.
  • A seat's boundary. A seat has a shell and runs as your own user, so on macOS the relay starts each seat's claude inside sandbox-exec, with a profile made for that seat. The seat and every program it starts cannot read or write GAMES_REPO, the games' sealed folder (GAMES_HOME, or ~/.games), the relay's state folder, the other seats' folders, and in ~/.claude the transcripts (projects), todos, file-history, session-env, plans and history.jsonl, which holds every session's prompts. It keeps its own folder, its own transcript folder and the files named with its own session id, and it may add to the hook queue without reading it. Add folders with RELAY_SEAT_DENY. A seat's environment also has no GAMES_REPO or GAMES_HOME. The boundary does not cover the network, your other files, or the other folders in ~/.claude, such as shell-snapshots. Where sandbox-exec is missing, a round gets 409 no_boundary, unless you set RELAY_SEAT_ISOLATION=off. GET /rounds/current says which: isolation: "sandbox" or "none".
  • A restart. A round never outlives the relay that ran it. Each seat is saved with its round's id, so the next relay brings no seat back: the session host hangs them up, the seat folders go, and the log says so in one line for each seat, with no brief.
  • A seat's hooks. A seat runs with OFFICE_SEAT=1, so its hooks drop every field that can hold its words (prompt, title, customTitle, message, tool_input, a huddle answer and a PR link) before they send or queue an event, and write nothing to OFFICE_HOOK_LOG. A notice that the seat waits for its next prompt keeps that fact as its notification_type. The relay drops the same fields for any hook it gets about a seat, also while a seat that ended is still closing.

Reaching it through a tunnel

A caller on another computer or in the cloud cannot reach localhost, so put a tunnel in front of the world's own relay (see One relay per world). Then the tunnel reaches that world alone, with its key, and not the room. For example, for a world on its relay at 8788, with Cloudflare's quick tunnel:

cloudflared tunnel --url http://localhost:8788

It prints an https://...trycloudflare.com address. Use that address as the caller's base URL, and open the world at the same address with /<folder>/?channel=<channel>&key=.... A quick tunnel gets a new address each time it starts. Check your company's rules before opening a tunnel from a work machine. The relay can keep listening on 127.0.0.1, since a tunnel connects locally. The room's own routes stay closed through a tunnel, and a tunnel that rewrites Host to localhost makes every request look local, so use one that passes its own hostname through (see hooks from another computer).

Remote mode: Cloudflare Access for one owner

A tunnel makes every request reach the relay from cloudflared on this computer, so each one looks local, and Cloudflare Access would be the only lock. Remote mode makes the relay check the sign-in too, so a wrong Access setting cannot open the room. It is off by default (relay/cf-access.js). Turn it on in .env with RELAY_REMOTE=1 and the four settings in Settings. With RELAY_REMOTE=1 and a setting missing, the relay does not start.

A request is remote when its Host is the public address, or it carries any Cf-Access-Jwt-Assertion, Cf-Ray, Cf-Connecting-Ip or Cf-Visitor header. For a remote request, any route, the page included, the relay reads Cf-Access-Jwt-Assertion and answers 403 with the word Forbidden and nothing else, unless all of these hold:

  • The signature is RS256 and checks against the team's public keys, from https://<team domain>/cdn-cgi/access/certs. The relay keeps them for an hour, and fetches them again, at most once a minute, for a key id it does not know. It uses only Node's built-in crypto.
  • The audience tag is the application's, and the issuer is https://<team domain>.
  • The token has not expired, and is not before its nbf.
  • The email is the owner's, ignoring case.
  • The amr list, the authentication methods, holds mfa. With RELAY_ACCESS_MFA=cloudflare the relay skips this one, and the Access application's own MFA setting must require MFA instead. Google sends no amr, and the token shows no sign of the Access application's own MFA step either, so with Google there is nothing in the token for the relay to check.
  • The Origin, if the request has one, is the public address.

A request that is not remote, such as the room page at http://localhost and every hook, is not changed: hooks never use the tunnel. A passing check adds a lock and removes none: the relay key and the local-only rule still apply, so through the tunnel the room's own routes stay closed: they refuse any request with a Cf- header, whatever its Host. With RELAY_REMOTE_FULL=1 (see Settings), a request that passed the check in this same request counts as local for that rule instead, so the owner can use the whole room at the public address. The relay key, the Origin check above and Sec-Fetch-Site (same-origin or none) still apply, and a request with a Cf- header that did not pass is refused as before. A valid token with Origin: null gets 403, since only the public address passes.

What remote mode trusts. Cloudflare to sign tokens only for people who passed the Access policy, the team's keys as the relay fetches them over https, the owner's identity provider to say mfa in amr (or, with RELAY_ACCESS_MFA=cloudflare, the Access application to require MFA, which the relay cannot see), and cloudflared to pass the public hostname or its Cf- headers. What it does not. It does not read a cookie or a session of its own, and it does not stop a program on this computer that sends a request with no Cf- header and a Host of localhost, since that is local use. It supports one owner: no list of emails, no portal. It changes nothing about session tokens. The check runs once for each request, so a stream that is already open stays open after its token expires. A key that Cloudflare revoked before the relay's hour is up still passes until the relay fetches the keys again.

Limits

  • Commands go only to a page that is open and visible.
  • Everything but the room's files in its state folder (tasks, tickets, sessions and the rest) is in memory. Restarting the relay clears channels, results and events.
  • One key for everything. Anyone with the key can drive any channel.
  • The relay has no general rate limit. A session's chat posts must be 5 seconds apart on a ticket's channel, or 60 on a fun channel, and a session files no ticket while Triage holds 20. Each answers 429 past its limit. Keep it behind a tunnel you control, and stop it when you are done.
