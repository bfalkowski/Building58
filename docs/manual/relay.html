The relay API and routes

The relay is a small server between callers and the world pages, such as the room. This page has its calls, its errors, its events, the room's API, the room's routes, and the scripts that drive it.

What the relay is

Each world runs in a browser page, and nothing outside the browser can call into a page directly. The relay (relay/server.js, Node 18 or later, no dependencies) sits in the middle. Callers such as curl, a script or an agent send commands to the relay over HTTP. The relay passes each command to the page, waits for the result and sends it back. The page also sends every event to the relay, where callers can read them or have them posted to a webhook. shared/relay.js connects a world page to the relay when it is opened with ?channel=, and uses only window.run.

The relay also serves the page, so the world and the relay share one address. That avoids the browser's cross-origin and local-network blocks, and once the relay is behind a tunnel the same URL works for any caller and any browser. It serves files from the repo folder (RELAY_ROOT): the room at /office/, any other world at its folder's name, this manual at /docs/manual/, and the root links to the room. It does not serve dot folders such as .git, or any folder named relay or node_modules, in any case, so /RELAY/server.js gets 404 too. It refuses any path with a character that is not ASCII, since macOS reads some of them as plain letters. A path with a malformed escape, such as /%E0%A4%A, gets 404. An unknown route under /channels/ gets 404 with not_found, and a channel name with a malformed escape, such as /channels/%E0%A4%A/tickets, gets 400 with the relay key with bad_channel.

Worlds. The relay does not know any world by name. A world is a folder in RELAY_ROOT with a world.json: name and channel make its link, port is where its own relay listens, and "sessions": true says its page runs Claude Code sessions, the Board and Autopilot. For example, { "name": "the office", "channel": "office", "port": 8787, "sessions": true }. A folder with no world.json, or one that is not valid JSON, is not a world, but with no RELAY_WORLD its files are still served. A world's own scripts live in its folder. A world can live in a repo of its own and be linked into RELAY_ROOT as a folder link: the relay serves it like any other folder. The rule is in CLAUDE.md and article 13 of the constitution, and relay/test/worlds-apart.test.js fails if code in relay/, office/ or shared/ names another world.

One relay per world. RELAY_KEY=a-key npm run world -- <folder> (relay/world.js) starts a relay for that world alone, on the port in its world.json. It sets RELAY_WORLD, which you can also set yourself, and PORT to the world's port unless you set it. RELAY_WORLD is one folder name: a trailing slash, as tab completion gives, is dropped, and anything else, such as a/b or /, stops the relay with the reason. Give each world its own key. The rollback check is for the room's relay: it looks for the room page and its sessions, so leave RELAY_ROLLBACK off for another world. Such a relay:

  • prints one link, its world's, and sends its root (/) to its world's folder;
  • serves only its world's folder, shared/, docs/ and the files at the top of the repo, such as README.md. Another world's folder gets 404, so a link into another world works only on that world's relay;
  • for a world without "sessions": true, never loads the room's parts: no sessions, tasks, tickets, Board, chat board, reviews or Autopilot, no polls to GitHub, and no files in the state folder. Their routes get 404. Commands, results and events work as for any world;
  • keeps running when another world's relay restarts or stops, and its key opens nothing in another world.

npm run office starts the room's relay this way, with RELAY_WORLD=office. npm run relay, with no RELAY_WORLD, still serves every world from one relay with the room's parts, on port 8787. /health says which world a relay serves, as world, or null for every world.

The page

The page connects to a relay only when its address has a channel:

ParameterMeaning
channelThe channel to join: 1 to 64 letters, numbers, dashes or underscores.
keyThe relay key.
relayThe relay's address, if it is not the server the page came from.
othersA world can read parameters of its own, such as the room's below.
timeThe room only: day, evening or night, the same as picking the light.
holidayThe room only: a holiday to show now (newyear, easter, july4, halloween, thanksgiving or christmas), the same as picking it under Holiday, or off for no decorations on that page. See Holidays.
lookThe room only: baked for the room's light baked in Blender, for each time of day, with fx=off to leave out its effects. See The baked look.

The world only runs while its page is on screen. Each page tells the relay when its tab is hidden or shown, and the relay log says so. If more than one page joins the same channel, commands go to the newest page that is on screen, or to the newest page if none is. A command sent to a hidden page waits and then times out, and the reply says that the tab is hidden (pageHidden: true). It is simplest to use a different channel for each page.

Calls

All calls to /channels/... need the key, as Authorization: Bearer <key> or ?key=<key>. Bodies are JSON.

CallWhat it does
POST /channels/{channel}/commandsSend a command and, by default, wait for its result.
GET /channels/{channel}/commands/{id}Get the result of a command sent with wait: false.
GET /channels/{channel}/eventsRead events the page has sent.
GET /channels/{channel}How many pages are connected (pagesConnected) and on screen (pagesVisible), and other counts.
POST /channels/{channel}/pages/{page}Used by the page: {"visible": false} when its tab is hidden, true when it is shown.
GET /healthThe relay is up, and which channels have pages. No key needed. With the key, from this computer, it also has restore: whether bringing back the saved sessions is done, and which could not come back, for the rollback check.

For example, with the room open on channel office, on its own relay (npm run office, port 8787):

curl -s -X POST http://localhost:8787/channels/office/commands \
  -H "Authorization: Bearer pick-a-long-random-key" \
  -d '{"action": "say", "who": "marcus", "text": "Hello", "source": "curl"}'

Send a command

POST /channels/{channel}/commands. The body is a command, the same as run.do() takes (see the world's own API, such as the room's API), plus fields for the relay:

FieldDefaultMeaning
actionrequiredOne of the world's actions. The room's are below.
source"relay"Your name, shown on every event the command causes. For a script, something like "script:standup".
atnoneRun the command at this many seconds into the run.
waittrueWait for the result. With false, the reply is 202 with an id to poll.
timeout30Seconds to wait, from 1 to 120.
 
{ "action": "say", "who": "marcus", "text": "Hello", "source": "script:standup" }

The reply is the world's result with the command's id, channel and action added:

{ "id": "ba29db55-d4bf-40e1-a99b-9ba42c0652b6", "channel": "office", "action": "say",
  "ok": true, "who": "marcus" }

When the world refuses a command, the reply is still 200, with ok: false, an error and a message (each world lists its own errors):

{ "id": "30b74e34-...", "channel": "office", "action": "dance",
  "ok": false, "error": "unknown_action", "message": "Unknown action \"dance\". Actions: ready, state, roster, ..." }

So a caller checks ok to see whether the world did it, and the HTTP status to see whether the relay could deliver it:

StatuserrorMeaning
200The world answered. Check ok.
202Accepted with wait: false. Poll /commands/{id}.
400bad_command, bad_request, bad_channelNo action, the body is not JSON, or a bad channel name.
401unauthorizedMissing or wrong key. The message says which.
403local_only, and others such as not_allowed or lead_onlyA room route asked from anywhere but the room page on this computer, or a token asking for what it cannot do. See the room's routes.
409such as wip_limit, lead_limit, bad_moveA room route refused a move or a start, and the message says why.
404not_found, unknown_commandNo such route or command id.
413bad_requestThe body is over 256 KB.
503no_pageNo page is connected to the channel.
504timeoutThe page did not answer in time. The command may still finish; poll its id. pageHidden: true means the page's tab is hidden, so its world is paused.

Some commands take time in the world, such as wait, which takes as long as you ask. Set the caller's own HTTP timeout above the longest command you send.

Poll a command

GET /channels/{channel}/commands/{id} returns { "status": "pending" } or { "status": "done", ...the same reply as above }. The last 500 commands per channel are kept.

Read events

GET /channels/{channel}/events?since=0&types=result,worker.assigned&limit=200

{ "ok": true, "channel": "office", "lastEventSeq": 42,
  "events": [ { "rseq": 41, "type": "worker.assigned", "who": "marcus", "label": "T-17", "source": "relay", ... } ] }

rseq is the relay's own sequence number for the channel. Pass the last one you saw as since to get only newer events. Every event also keeps its fields from the page. The last 2,000 events per channel are kept. The relay keeps them in memory, so a restart clears them.

Webhook

With RELAY_WEBHOOK_URL set, the relay posts batches of events as they arrive:

{ "channel": "office", "events": [ { "type": "worker.assigned", "who": "marcus", ... }, { "type": "result", "action": "say", ... } ] }

RELAY_WEBHOOK_AUTH is sent as the Authorization header, and RELAY_WEBHOOK_TYPES picks which event types are sent. A failed post is logged and not retried.

The room's API

The room has window.run, the same contract as every world, so shared/relay.js and the relay work unchanged. Every action can be sent through the relay as {"action": ...}. The Claude Code hook sends {"action": "hook", "event": {...}, "wait": false} (see hooks).

ActionParametersWhat it does
hookevent: a hook payloadWhat the Claude Code hook sends. See How events become work.
workwho or skill, labelSends someone to work, from outside a session. With skill, a free person with that skill in the roster.
activitywho or skill, text, kindA line on their monitor. kind: edit, read, bash, web, tool or fail.
donewho, skill or all: trueFinishes work.
sessionslistThe sessions the relay runs. The panel sends this so each has a person.
taskslistThe tasks for the wall board. The Tasks panel sends this.
waitingmessageThe lead raises a hand. Send no message to clear it.
idlewho, doSends someone who is not working to coffee, couch, window, chat, board, desk, fridge or pingpong.
saywho, textA speech bubble.
managernoneSends the manager through now.
partyon: true or false (anything else is refused), or left out to toggle; seconds: 5 to 600, 60 if left outThrows a party for that long, or ends the one going on. See Throw a party. run.state().party says whether one is on, how many seconds are left and who is at it.
resetnoneEnds all work and clears the board.
state, roster, readynoneA snapshot, the people, and a wait until the room is built.
speedvalue: 0 to 8How fast people move. Work state does not depend on it.
waitsecondsWaits.

Events: office.started, office.live, time, worker.assigned, worker.finished, worker.doing, lead.waiting, lead.unblocked, manager.arrived, manager.left, party.started, party.ending (the candles go out), party.ended, hook, and action and result for everything except hook.

In the browser console, run.view('desks') moves the camera (home, desks, lead, coffee, lounge, board), run.focus('marcus') follows someone, run.time('night') changes the light, and run.holiday('christmas') shows a holiday's decorations ('auto' goes back to the date, 'off' and 'on' set the switch this browser keeps). run.state().holiday says what is up and which holiday is next.

The room's routes

These are under /channels/{channel} and answer only the room page on this computer (see the local-only rule), while RELAY_TERMINAL=1. They take the relay key, or a session's token as described below.

RouteWhat it does
GET, POST /ticketsList or file tickets. The list comes in Board order: open tickets high, normal, low, in work order (rank) within each, then done and rejected ones, the latest changed first. It also has kinds (the kinds a ticket can have, see Kind), wipLimit, leadStarts (the number you let the Lead start tickets up to, or 0) and leadStartsLeft. A ticket has approvedBy (you or Lead) once it is put in Ready. The room page gets the same list as a tickets event on its GET /stream when it opens the stream with board=1, with people, who sits on each ticket, and without the time each pipeline was checked. The stream's hello says whether it will (tickets). It is sent once as the stream opens, then only when it changes, and only to the room page on this computer.
GET /tickets/{id}One ticket.
POST /tickets/approve-readyMarks the Ready tickets that no person approved as approved by you, as Approve all Ready does: those in ids, or every one with no ids. It skips a ticket that is starting. Answers with the ids in approved. No session's token reaches it.
POST /tickets/{id}/move{"to": ...}: move a ticket that has no task, as Approve, Reject, Back to Triage and Merged elsewhere do (with pr for done).
POST /tickets/{id}/startStart a Ready ticket: a task, a checkout and a worker. A Lead's token is held to its limits.
POST /tickets/{id}/priority{"priority": ...}: high, normal or low for a Triage or Ready ticket. It goes last in its new priority. A priority it already has changes nothing, and the answer has unchanged. The person's key, or the token of a PM or Lead you let set the order (The PM sets the order, The Lead sets priority). Any other session's token gets 403.
POST /tickets/{id}/order{"before": id} or {"after": id}: a Triage or Ready ticket goes next to another Triage or Ready ticket with the same priority. Usually only the moved ticket is written. When there is no room between two ranks, the Triage and Ready tickets of that priority are numbered again. If the store fails partway, the ranks already written are put back and the answer is 502. Those tickets keep a new updatedAt. The person's key, or the token of a PM or Lead you let set the order. Any other session's token gets 403.
POST /tickets/{id}/kind{"kind": ...}: a Triage or Ready ticket's kind. A new word adds a kind, and "" takes it away. Refused while it is starting, and once it has started.
POST /tickets/{id}/base{"base": ...}: a Triage or Ready ticket starts from another local branch. Refused while it is starting, or when another open ticket has that title on that branch.
POST /tickets/{id}/edit{"title", "body", "priority"}, any of them: changes a Triage or Ready ticket's words, with the limits of filing one (a title of 1 to 80 characters, a body of up to 8000, high, normal or low). Only the fields that differ are written, and the answer has unchanged when none do. Refused while it is starting or once it has started, is done or is rejected (409, or 403 for a session's token), and when another open ticket in the repo has the new title on its branch (409). For the PM and the Lead, a ticket you rejected counts too, as in filing. The answer's edited lists the fields that changed. A new priority puts it last in that priority, as /priority does. See Editing a ticket.
POST /tickets/ask{"idea", "repo"}: starts the PM.
GET, POST /tasksList or start tasks.
GET /tasks/{id}One task.
POST /tasks/{id}/move{"to": ...}: building, in_review, changes_requested, waiting_on_you or done.
POST /tasks/{id}/resume, /cleanBring back its worker, or remove its checkout.
GET, POST /checkoutsList checkouts, or start a session in a new one. A review of a PR can send unlessAt, the commit its last review read. While the PR is still at that commit, nobody starts and the answer says unchanged.
POST /checkouts/{id}/cleanRemove one.
GET, POST /reviewsThe automatic reviews (see Automatic review). auto and again are the two switches, and a POST with either one, true or false, sets it. The answer also has max, each PR with its count, head, pending and waits, and news, what the relay said about the reviews it started, which the page shows once.
GET, POST /terminalsList or start sessions. The list also has finished: the latest automatic reviewers that posted and left. Answer the offer to bring it back (asked: true; POST /terminals with resume and lead: true is what Bring back sends). With board: true or false, give or take away its permission to move the board. What a session's token reaches

Each session the room starts gets OFFICE_TICKET_TOKEN, sent as X-Office-Token. Tokens reach nothing but this:

  • Any session's token can GET and POST /tickets, except the COO's, which can only GET it.
  • Any session's token can POST /commands, but only {"action": "hook"} with an event about its own session: the hook sends that way to OFFICE_HOOK_URL. The relay sets the event's terminal to that session's desk. A SessionStart may carry a new session id, after /clear. Anything else gets 403.
  • Any session's token can POST /terminals/context, but only for the conversation its session is in now: its status line says how full its context is (How tired the Lead is).
  • Any session's token but the COO's and the security officer's can GET /chat and /chat/{name}, and POST /chat/{name}. A post that mentions a session is typed into it, and those two only propose. Their tokens can list tickets but not file them.
  • A reviewer's token can also POST /autopilot/verdict, for the PR it reviews. No token reaches /autopilot itself.
  • The Lead's token can also GET /floor.
  • The token of a session you made the Lead and let move the board can also POST /tasks/{id}/move and /tickets/{id}/move, and GET /tasks, which then shows only each task's id, state, title, branch and PR. With RELAY_LEAD_STOPS=1 it can also POST /floor/stop. While Autopilot is on, a move is refused with 403 and autopilot unless it takes a task, or a ticket with no task, to Done once the relay has seen its PR merge. See The Lead under Autopilot.
  • The COO's token can also GET /coo/measures and POST /coo/report.
  • The security officer's token can also GET /security/measures and POST /security/report.
  • The token of a session you made the Lead and let start tickets can also POST /tickets/{id}/start, within the limits in The Lead starts tickets, and never while Autopilot is on. While a round of a game runs, it gets 409 with held (see Games).
  • A seat's token, in a round of a game, reaches only POST /play, its own hooks on /commands and its status line on /terminals/context. Everything else, tickets and the chat board included, gets 403.
  • The PM's token can also POST /tickets/{id}/priority and /tickets/{id}/order, but only while Let the PM set the order is on, only for a ticket in Triage or Ready, and only for the PM that started last on the channel. Otherwise it gets 403. The relay checks the switch again when the request's turn comes, so a request that was waiting when you turned the switch off is refused too. A ticket set this way has orderedBy PM, and one you set has you, with orderedWhat priority or place.
  • The PM's and the Lead's tokens can also POST /tickets/{id}/edit, for a ticket in Triage or Ready. A new priority in it needs the same switch as /priority, or the whole edit gets 403. A ticket that is starting, started, done or rejected gets 403. A new title or body on a Ready ticket you approved takes your approval back, and the answer has approvalTaken.
  • The Lead's token can also POST /tickets/{id}/priority and /tickets/{id}/order, but only while Let the Lead set priority is on, only for a ticket in Triage or Ready, and only while the session is still the Lead. It does not need Let the Lead move the board. Otherwise it gets 403. The relay checks the switch again when the request's turn comes. A ticket set this way has orderedBy Lead.

    • Other routes answer a token with 401. /tickets/{id}/priority and /tickets/{id}/order answer every other token with 403, and so does /tickets/{id}/edit for every token but the PM's and the Lead's. The PM's token gets 403 on /tickets/{id}/move, /start, /base and /kind.

    Games

    The room can act out a game from another repo for one round. The room does not change, only the roles of the sessions in it. Set GAMES_REPO to a folder of games. A game is a folder in it with a game.json: {"name", "version", "api": 1, "entry", "players": {"min", "max"}, "needs"}. This relay can meet the needs privateBriefs, ask and files. No code in relay/, office/ or shared/ names a game, and relay/test/games.test.js checks that when GAMES_REPO is set.

    A round runs the game's entry with node, in the game's folder, as its own process, without the relay's key. They talk in JSON lines. The relay sends hello, setup (seed, settings, seats), action (id, seat, kind, args), finish and abort. The game sends hello, brief (seat, text), ready, answer (id, text), spend (usd) and done (score, reveal).

    • Seats. Each seat (S1, S2 and on) is a fresh session at a free desk, in a new folder that is not a copy of a repo, with no task. Every seat folder sits under one parent, ~/.office-world/seats/<round>/<seat>, and goes when its seat ends. Its brief is typed as its first prompt and kept nowhere else: not in a file, the relay's log, a title or a route. A seat's hooks reach the room without their words. The relay has no field for a role. Only the game knows who is what.
    • Playing. A seat runs node "$OFFICE_PLAY" ask "a question", or another kind its brief names, and gets the game's answer. Its folder is empty, so the relay gives it the full path of relay/play.js as OFFICE_PLAY. The game routes answer only the room page and the sessions on this computer, like every room route.
    • Watching. A round is watch: "all" (the default): you can open any seat's screen. Or "none", for when you play too: a seat's screen is refused with 403 until the round ends. Either way a seat is read-only to you: typing into it gets 403. The one exception is Claude Code's question about trusting the seat's folder. Nothing is typed into a seat while that question is up, so GET /rounds/current shows that seat with waiting: "trust", and you may answer it. You can also trust ~/.office-world/seats once in Claude Code, if it honors a parent folder's trust for the folders under it. That is not checked yet.
    • The rest of the room. While a round runs, the Lead and Autopilot start no new tickets. Work already running goes on.
    • The end. Finish shows the game's score and reveal, and a second Finish while the first waits gets the same answer. Stop ends it with no score. A game that exits, sends a line that is not JSON, or does not answer for RELAY_GAME_TIMEOUT_MS (30 seconds) ends its own round, and so does a round that reaches its spend cap. Then every seat is stopped and its folder removed. The relay keeps only each round's id, game, time and score, while it runs.
    • A seat's boundary. A seat has a shell and runs as your own user, so on macOS the relay starts each seat's claude inside sandbox-exec, with a profile made for that seat. The seat and every program it starts cannot read or write GAMES_REPO, the games' sealed folder (GAMES_HOME, or ~/.games), the relay's state folder, the other seats' folders, and in ~/.claude the transcripts (projects), todos, file-history, session-env, plans and history.jsonl, which holds every session's prompts. It keeps its own folder, its own transcript folder and the files named with its own session id, and it may add to the hook queue without reading it. Add folders with RELAY_SEAT_DENY. A seat's environment also has no GAMES_REPO or GAMES_HOME. The boundary does not cover the network, your other files, or the other folders in ~/.claude, such as shell-snapshots. Where sandbox-exec is missing, a round gets 409 no_boundary, unless you set RELAY_SEAT_ISOLATION=off. GET /rounds/current says which: isolation: "sandbox" or "none".
    • A restart. A round never outlives the relay that ran it. Each seat is saved with its round's id, so the next relay brings no seat back: the session host hangs them up, the seat folders go, and the log says so in one line for each seat, with no brief.
    • A seat's hooks. A seat runs with OFFICE_SEAT=1, so its hooks drop every field that can hold its words (prompt, title, customTitle, message, tool_input, a huddle answer and a PR link) before they send or queue an event, and write nothing to OFFICE_HOOK_LOG. A notice that the seat waits for its next prompt keeps that fact as its notification_type. The relay drops the same fields for any hook it gets about a seat, also while a seat that ended is still closing.

    Reaching it through a tunnel

    A caller on another computer or in the cloud cannot reach localhost, so put a tunnel in front of the world's own relay (see One relay per world). Then the tunnel reaches that world alone, with its key, and not the room. For example, for a world on its relay at 8788, with Cloudflare's quick tunnel:

    cloudflared tunnel --url http://localhost:8788

    It prints an https://...trycloudflare.com address. Use that address as the caller's base URL, and open the world at the same address with /<folder>/?channel=<channel>&key=.... A quick tunnel gets a new address each time it starts. Check your company's rules before opening a tunnel from a work machine. The relay can keep listening on 127.0.0.1, since a tunnel connects locally. The room's own routes stay closed through a tunnel, and a tunnel that rewrites Host to localhost makes every request look local, so use one that passes its own hostname through (see hooks from another computer).

    Limits

    • Commands go only to a page that is open and visible.
    • Everything but the room's files in its state folder (tasks, tickets, sessions and the rest) is in memory. Restarting the relay clears channels, results and events.
    • One key for everything. Anyone with the key can drive any channel.
    • The relay has no rate limits. Keep it behind a tunnel you control, and stop it when you are done.
