How the room works

A loft in New York, where each developer is one of your Claude Code sessions. This page says how work moves between GitHub, the relay, the browser and the sessions. It describes the code on main as of 2026-11-04. It shows only what is built.

The map

Four places, with you at the top. The relay is the hub: it runs every Claude Code session as a child process, hears every hook, serves the page, and is the only part that talks to the page. GitHub is reached through gh and git, with your own login.

You Browser Relay Claude Code GitHub

The page never runs anything

It asks the relay. Even Refresh the Lead is a request: the relay does the typing, because only it knows whether a prompt is safe to type into.

The relay drives every session

Sessions run in the session host, which the supervisor starts. The supervisor restarts the relay after Update, and the new relay takes each session back, still running. Stop the relay and they stop, and the next start brings each back with claude --resume. See Bringing a session back.

Sessions are plain Claude Code

They get a brief typed as their first prompt, a token for ticket.js, and their own checkout. The relay's key is taken out of what they inherit.

GitHub is the outside world

Code leaves the computer only as branches and PRs. The relay reads PRs, comments and CI with gh, and writes issues only if the GitHub ticket store is on.

A ticket's life

One ticket, from idea to running code. Each step sits in the lane of whoever does it. Dashed steps are the ones a person still does, or that need a switch you turn on. The Board's side of this, column by column, is in The life of a ticket.

Hooks up, typing down

Two flows keep the room alive. Up: Claude Code tells the relay what each session is doing, through hooks. Down: the relay types into sessions, but only when it is safe. Silence never counts as idle: only a hook says a turn has ended.

Where the hooks come from

Either installed once in ~/.claude/settings.json with npm run office:hooks, pointing at one relay and channel, or, without those, given by the relay to each session it starts with claude --settings. See Sessions from your own terminal.

Why "safe to type" matters

Text and Enter answer whatever is on screen. Typed on a guess, a message could approve a command nobody read, or be joined to what you were typing.

What the page does on its own

Nothing that moves work. The relay starts every automatic review, so they start with the tab closed. The page sends what you press and shows what the relay says.

What the hook sends

relay/office-hook.js trims each event before it leaves the machine:

Hooks from another computer are ignored. The relay changes no state, title or message for a hook event unless it came from this computer, because that state decides when anything is typed into a session, the Lead's brief included. Hooks run on this computer and post to localhost, so nothing real is lost. The page still shows such an event. A tunnel that rewrites Host to localhost makes every request look local, so use one that passes its own hostname through.

Typing into sessions

The relay types briefs, saved messages, review news, huddle questions and the steps of Refresh the Lead. Before each one it asks notSafeToType, drawn in the figure above, and checks again right before Enter.

Saved messages (relay/delivery.js, kept in RELAY_DELIVERIES_FILE) are typed only when:

  • hooks say the turn has ended,
  • nothing has printed for a moment,
  • no menu or trust question shows in the last of the output,
  • a ❯ shows somewhere in the last 16 KB of it,
  • and nobody has left text in the prompt.

Text of 800 bytes or more, such as a brief, goes in as one paste. Typed as plain keys, Claude Code reads a long text about 1024 bytes at a time and keeps only the last piece. Bytes count, not characters, since a letter outside plain English can take two bytes or more. This holds for every message, a session's first brief included. The Lead's brief names ticket.js by its full path, so it is longer when the checkout's folder path is long, and it still arrives whole, however long that path is.

A key you press holds typing until Enter, Ctrl+C or Ctrl+U, even if you deleted what you typed, unless a menu was up when you pressed it. The check runs right before typing. Silence never counts as idle. Saved messages survive a relay restart, and reach a session brought back with the same id once a hook has been heard from it. While an update is under way, nothing is typed.

A first brief. A task's brief and the Lead's brief are saved messages too. Nothing else is typed into that session before its brief. The Lead's brief counts as in once it is typed, since a Lead with no hooks reaching the relay is still briefed. A task's brief is in only once a hook says a turn began after it was typed: typed alone does not count, so the task says brief not in yet until then, and the brief stays saved until then. If the worker ends first, the brief waits for that session id: a session brought back with the same id gets it again, and Bring back on a task whose brief is not in starts the worker over and gives it the brief. A relay restart keeps it: a worker that ran on through the restart is watched again from when the brief was typed, and is not typed into twice.

A first prompt. A reviewer's (from Get a review too), the PM's and the COO's first prompts are first briefs too, and each is in only once a hook says a turn began after it, as for a task's brief. Until then it is saved, both as a saved message and with its session. Three things differ. An update holds it only while the relay restarts, not while the update waits for a quiet moment (see What holds a restart). If its session is not ready for it within RELAY_READY_LIMIT, counted again from when a relay comes back, or the session ends while the relay runs, the relay gives up on it and writes why in its log. And the relay tries it three more times, not once, before it calls the session stuck (below), since Claude Code can drop the Enter that follows a long paste and leave the prompt in its box. A session that ran on through a relay restart is watched again from when its prompt was typed. A session nobody spoke to comes back after a stop with a new session id and a new desk, and its prompt goes with it, typed again there.

A session that does not start. After a saved message goes in, such as review news, a Lead comment or a chat mention, the relay checks that a hook says a turn began within a minute (RELAY_TOLD_CHECK_MS). If none did, it tries once more (three more times for a first prompt), when it is safe to type: Enter if the message still shows since its last Enter, or the prompt cleared with Ctrl+U and the message typed again if it does not. It does not try while a menu or question is on the screen, since Enter would answer it. If no turn begins a minute after its last try, the session is stuck. The relay stops trying and leaves it to you. It never types a message again into a session that began a turn after it.

  • The Floor says stuck: told 27 min ago, did not start, counted from when it was first told, and the next step says why, where the relay can tell from the screen: a menu is open, it is asking whether to trust its folder, someone has text in its prompt, its screen shows no prompt, or the message is still in its prompt, not sent. Otherwise it says the relay cannot tell why. ticket.js floor shows the same, so the Lead sees it.
  • #office, and the ticket's chat channel, say once that it is stuck and why. For a first prompt they say so, and for a reviewer they name its PR: Ravi on T-12 did not start on its first prompt, the review of PR #154, so it is stuck: the note is still in its prompt, not sent. The relay stopped trying after 3 more tries. Open its session and press Enter if the prompt is still in its box, or answer what is on its screen. Stopping it drops the prompt. The Floor's next step says the same. A reviewer, the PM or the COO has no task to Bring back, and stopping one drops its prompt, so open its session instead.
  • Nothing else is typed into a stuck session. Other messages for it wait.

What to do. Open its session on the Floor. Answer the menu or question, or press Enter if the message is still in its prompt. Once a hook says a turn began, it is not stuck, and the messages that waited go in. If the session does not answer, stop it and press Bring back on its task: the message is kept for that session id, so the session brought back gets it once it is idle. A reviewer, the PM or the COO stuck on its first prompt has no task to bring back, and stopping it drops the prompt, so open its session and press Enter there instead. Stuck is kept only in the relay's memory, so a relay restart forgets it (T-53).

Is a session alive. One module, relay/liveness.js, answers this for every session, from all the relay sees of it together: what its hooks last said, when it last printed, and whether its process ended. The Floor, ticket.js floor, Autopilot's stall check and the COO's stall count all ask it, and none of them reads hooks for this on its own. Its answer is one of these:

  • working: in a turn, and a hook came within the stall time.
  • quiet: in a turn, no hook for the stall time, but it printed something within that time. The Floor says quiet: no hook for 34 min, its screen still moves.
  • stuck: in a turn, with no hook and no output for the stall time. The Floor says stuck: no hook and no output for 31 min, counted from the later of its last hook and its last output, and its next step waits on you. A session that did not start on a message is stuck too, as above.
  • gone: its process ended, or it was stopped. It leaves the Floor.
  • Out of a turn, it is waiting on you or idle, as its hooks say. A session waiting on you is never stuck, however long: the question is yours.
  • job: out of a turn, but a command it started still runs, such as npm test sent to the background. It is busy, not idle: Autopilot does not count its task as stalled, Update waits for it, and it is not safe to stop, since a stop would end the command. The Floor says job: its turn ended 4 min ago, and a command it started still runs, and its desk line says running a job. Once the command ends, it is idle.

How the relay sees a job. Hooks cannot say when a command in the background ends, so the relay reads the process tree instead. Every 5 seconds the session host runs ps once and looks at the children of each session's claude process. A child is a job when it is a shell run with -c that sources Claude Code's shell snapshot (~/.claude/shell-snapshots/), which is how the Bash tool runs every command, or any shell run with -c that has run for a minute. Every other child is a helper and does not count: caffeinate, which Claude Code starts while it works, MCP servers, and hook and status line commands, which end within seconds. The host tells the relay only when a session's jobs change. A session host started before this change does not look, so its sessions are never job until you stop the relay and start it again once.

The stall time is A session is stuck after in Settings, under Work (30 minutes, RELAY_STALL_MS). Only a hook counts as progress. Claude Code's spinner and its timer keep printing while it thinks and while a long command runs, so output says only that the process is alive and drawing. Output never makes a session working. It only keeps a session whose hooks went silent from being called stuck. A quiet session may be thinking, running a long command, or sending hooks that no longer reach the relay, and the relay cannot tell which, so nothing acts on quiet by itself. A quiet session whose output stops too becomes stuck once the stall time has passed since its last output. After a relay restart, the stall time counts again from when the new relay took the session back.

What you see on the page

While a session works, its developer types at their desk with its tool calls on their monitor (edit src/cart.ts, $ npm test). When it needs your permission, they raise a hand and the tab title counts them. When its turn ends, they stretch and go back to the coffee machine, the couch, the window, the bar table or the ping pong table until you give it the next prompt. So the room replaces your terminal tabs. What each sight means for you is in How to tell what is waiting on you.

  • Floor: everyone in the room. The Lead comes first, and its row stays at the top of the list while the rest scrolls under it. Then come the others, in the order needs you, working, ready for a prompt, free. Each row says what the person is on, with the ticket first: a Dev shows T-17 · Review comments reach the Dev and a reviewer shows reviewing T-17 · Review comments reach the Dev, followed by the PR if there is room. A reviewer shows Review PR #7 until a task has recorded that PR, and for good if no task ever does. The PM's row starts PM:. A session with no ticket, such as Add worker, shows its own title. Click the number to open that ticket on the Board. Click anywhere else on the row to show their session and follow them with the camera. Click again to stop following. Under that, each session the room started has its desk lines.
  • Scene: each name tag shows what that person is working on, and so do the Org chart and their monitor: the Floor's words without the PR, cut to 60 characters. A note on the wall board starts with its ticket's number. Clicking a person or their tag does the same as the Floor list. The first three people are always there. The rest come in for a session and leave when it ends.
  • Moving the view: drag to turn the scene, and scroll or pinch to zoom. The pad at the bottom right of the scene does the same, in the room and any world that attaches it, for anyone who finds dragging hard. The side arrows take the camera around to the left or right, the up and down arrows raise and lower it, + and − zoom, and the house goes back to the first view. Hold a button to keep going. With a pad button or the scene in focus, the arrow keys, + and - do a step, and Home or 0 goes back. The button between − and + hides the pad and leaves one button that shows it again. This browser keeps the choice, for every world, and with the pad hidden the keys still work with the scene in focus. The pad keeps each world's own limits on how far the camera turns and zooms. In the room it stops the opening glide and following a person, as a drag does. Without WebGL there is no scene, so there is no pad.
  • The manager's office: the Manager's office button at the bottom left of the scene puts the view behind the manager at his desk, over his head and out through the glass at the room. Drag, the side arrows or the arrow keys swing it around him, about 70 degrees each way and a little up and down: to the sofa and floor lamp on the left, the files on the right. The view is wider there, and the name tags of people out on the floor are hidden. It stays behind his chair, in front of the pin board, so it never goes through a wall, and + and − zoom only a little. Back to the room, the house, or following a person brings back the room's view. In the room, the view turns around a point on the floor, which a right drag can also slide into the office through the opening. Without WebGL there is no button.
  • Activity: who started and finished what, prompts, turns and permission waits.
  • Chat: under the Board, the chat channels and their posts. See The chat board.
  • Tasks: each task's state, worker, branch and PR. Click a task to see its worker.
  • The manager: someone in a suit works in a glass office off the back wall, behind the glass door under the clock. The room opens with him at work at his desk, and he goes back to it after each round. Between rounds he keeps busy in there: he works at his desk, leans back to think, takes calls at his desk or on the sofa, stands at the glass looking out at the floor, goes through the files, and reads the pin board. The office's floor lamp, desk lamp and ceiling light follow the room's Light: nearly off by day, warm in the evening, and warmer and brighter at night. He never leaves, so they never go out. Only he and the Lead walk into the office. With nothing to do, the Lead sometimes goes in, sits in a guest chair for a moment, and comes back out. The door opens for either of them as they come up to it, and the name on it is manager.title in office/roster.js.
  • The manager's rounds: every 6 to 15 minutes, he opens his door, comes out, looks around, and stands behind a few people. Behind most of them he says a line of tech buzzwords, such as "Can we make it more agentic?". He has 100 lines, in office/manager-lines.js, and says each once in a shuffled order before any comes round again. Anyone without real work hurries to a desk and types until he is back through his door. Sessions that are working or waiting carry on as they were, and the Floor list and tags keep telling the truth. So a person who looks busy may not be.
  • Holidays: the room decorates itself for the next holiday, from this browser's date, with no network call. A holiday's decorations go up 14 days before it and stay until the day after it. New Year's runs from Dec 26 to Jan 1, so it follows Christmas, and Christmas ends on Dec 25. On other days there are none. Easter is worked out for each year (the Gregorian computus) and Thanksgiving is the fourth Thursday of November.

    • Easter: pastel eggs on the window sills, the counter and in a basket by the board, and two bunnies.
    • The Fourth of July: red, white and blue bunting on the walls, and small flags.

  • The baked look: ?look=baked in the address. Blender has baked the room's light for each time of day: the light that bounces off the floor and the brick, and the soft dark where things meet. The bake covers the parts that never move and are at least 30 cm across, such as the walls, the floor, the desks and the couch. The page swaps those parts for a baked copy. What each desk says. Under the name, each Floor row for a session the room started says:

  • For a Dev with a task, a status icon with a short label beside it, so it reads without knowing the icons. It says where the Dev's PR stands, and the first of these that holds wins: ✅ merged or done, ✋ waiting on you (its task is in Waiting on you), 🔨 building (no PR yet), 🔍 being reviewed by the reviewer's name (or being reviewed before the page has named them), ❌ CI failed, ⏳ CI running, 🔧 fix requested (its task is in Changes requested, or the latest verdict says fix), 👍 review says merge, and otherwise 🕒 waiting for a review. A verdict counts only while CI is on the commit it read, so after a push the icon says waiting for a review again. The icon changes at the page's next look, as the relay learns of each step. The Lead, the PM, a reviewer and a session you added have none.
  • Who reviews whom. A reviewer's row sits right under the row of the Dev whose PR it reviews, indented with a line on its left, and says reviewing PR #31 for the Dev's name. That Dev's row says reviewed by and the reviewer's name, or each name when more than one reviews it. A reviewer whose PR has no Dev on the Floor stays a row of its own and says reviewing PR #31. The relay pairs them by PR (pairReviewers in relay/desk.js) and sends the pair with each desk in GET /floor.
  • What it is doing now: working, idle 12 min, waiting on you with the reason, such as a permission prompt, quiet: no hook for 34 min, output still moving, running a job: a command it started still runs, stuck: no hook or output for 31 min, or stuck: told 5 min ago, did not start for a session that did not start on a message the relay typed (A session that does not start). See Is a session alive. A stuck desk's next step waits on you and says why.
  • Its ticket's column on the Board, such as In review. A reviewer shows the column of the ticket whose PR it reviews. The ticket's number above it opens its card on the Board.
  • Its PR, as a link to GitHub, with the CI state the relay last heard (CI green, CI running, CI failed, no CI) and the review state (no review yet, review running, review says merge, review asks for fixes, review waits on CI, review waits for a desk, automatic reviews used up, automatic review could not start, or for a reviewer review posted).
  • One line for the next step and who owns it, such as Next: Autopilot merges when CI is green, Next: The reviewer reviews PR #31 (reviewer), Next: Waiting on you: constitution change or Next: Done, safe to stop. A step that starts Waiting on you is in amber. A review that waits on CI, the first one or one after a push, says review waits on CI. A Done Dev that cannot be stopped says why, such as Done, not safe to stop yet: it is working. A task in Waiting on you gives the reason Autopilot handed it over, or the note on the move that put it there.
  • Safe to stop with the reason and a Stop button, only when both the stop verdict and the two kinds the Lead stops allow it: an automatic reviewer that has posted, or a Dev whose PR merged or whose task is Done with all its work pushed. The Lead, the PM, a session you added and a Dev still at work never show it.

When any desk is safe to stop, Stop all safe appears in the bar at the top of the Floor with how many. It and each Stop send POST /floor/stop, and the relay asks the same verdict again at that moment, so a desk that started working since the page drew it is not stopped. You stop them, so Let the Lead stop sessions and the Lead's hourly limit do not apply. A stopped Dev keeps its checkout and branch, its task's history says you stopped it from the Floor, and Bring back returns it. The page asks GET /floor every 3 seconds. The relay builds each desk (relay/desk.js) from what it already keeps: tasks, the pipeline it polls, automatic reviews and Autopilot's last look. Drawing a desk asks GitHub nothing, so the CI and review words are as old as the relay's last poll.

Where a label comes from. A worker on a ticket shows T-17 · its title, and a reviewer of that ticket's PR shows reviewing T-17 · its title. The relay works this out (workOf in relay/tasks.js) and sends it as work with each session in GET /terminals, so a reload loses nothing. A worker on a task with no ticket shows the task's title for as long as the task lasts. Otherwise it is the session's title: the one Claude Code writes soon after the first prompt, or your own if you run /rename building worker labels in that session. It appears on their name tag, the Floor list, the board and their monitor at their next event. Claude Code does not document where it keeps titles, so if that changes, the label falls back to the skill or the project folder.

A title you give a session. Run /rename my title in a session the room runs, and my title shows right after that person's name, as Paul · my title: on their name tag in the scene, on their row in the Floor list, and in the Claude Code panel's header when their session is open. This works for every session the room runs: one you added, a task's Dev, a reviewer, the PM, the COO and the Lead. Only a title you set counts. The one Claude Code writes by itself does not show here. The hook sends it as customTitle, and the relay keeps it with the session in sessions.json, so it is still there after the relay restarts, and sends it as customTitle with each session in GET /terminals. More than 30 characters is cut with …, and the whole title shows when you hover over it. It is shown as text, never as HTML. When the label after the name would only say the same title again, it shows the project folder instead. A new conversation in that terminal, after /clear or /resume, starts with no title until its own transcript has one. The page reads it every 2 seconds. A session from your own terminal, which the room does not run, does not show one. The person's name stays as it was everywhere a name is matched, such as an @ mention in Chat, a huddle, node relay/ticket.js stop Paul and the Floor's names.

The room looks like a loft in New York: exposed brick, steel factory windows with water towers outside, cast iron columns, ductwork, Edison bulbs, a coffee bar and a couch. People are built from spheres, cylinders and boxes on a rig of joints (pelvis, spine, neck, shoulders, elbows, hips, knees), posed by joint angles in POSE. They walk on a 15 cm grid with A*, and each plan is a list of steps: stand, walk, face, sit, act.

Two rooms

A second room in a second tab, for a new project, with its tickets as GitHub issues. Run a second relay with its own port and its own state folder (RELAY_STATE_DIR), and, for issues, its own ticket store. A second room has the command.

Why a second relay, not a second channel

A channel is a separate room on the same relay, but the ticket store is set once per relay. Turning on GitHub issues for one channel would turn it on for all of them.

Why a new repo

Tasks work in their ticket's repo, so the new room's branches and PRs never touch 3d. The relay's own code stays in 3d.

Costs

Up to 18 sessions on one computer, and the relay writing the new repo's issues through your gh login.
