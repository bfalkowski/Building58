Running it

What the room does when you start it, connect sessions, restart it and update it. The commands to type are in office/README.md.

Starting the room

npm run office (relay/office.js) starts the relay if none is running at RELAY_URL, and opens the room on channel office with the command in OPEN_CMD. Open the link it prints if no browser opens. When it leaves the room running, it prints how to add the hooks for sessions from your own terminal (see Your own terminal), with <your relay key> in place of the key, so the key does not land in the log. For a second room it prints no such line, and says not to add the hooks (see A second room). It counts as a second room when RELAY_URL is not port 8787 on this computer, or the state folder is not ~/.office-world. It sets RELAY_TERMINAL=1 and RELAY_WORLD=office on a relay it starts, so that relay serves the room alone, and other worlds run on relays of their own (see One relay per world). It does not change a relay already running, which it reuses as it is.

npm run relay, with no RELAY_WORLD, serves every world and prints a link for each one it finds (see Worlds):

Relay on http://127.0.0.1:8787
Key: pick-a-long-random-key
Open the office: http://localhost:8787/office/?channel=office&key=pick-a-long-random-key

node relay/server.js is a small supervisor (relay/supervisor.js) that runs the relay as its child. When Update pulls new relay code, the relay exits with code 75 and the supervisor starts it again on the same port with the same key, even a random one. Ctrl+C stops both.

The session host. While RELAY_TERMINAL=1, as npm run office sets, the supervisor also starts the session host (relay/session-host.js). The host runs each session's pty-bridge.py and the claude in it, and keeps each session's last 256 KB of output. The relay drives the sessions through the host, over a socket in a folder only you can open, named to the relay in RELAY_HOST_SOCKET. So a restart of the relay does not touch the sessions: a turn in progress goes on, and the panel shows the same output. When the supervisor stops, it stops the relay first, so the relay saves its list, then the host, which ends every session. If the host stops by itself, every session ends with it, and the relay restarts and brings them back as after a stop. The supervisor and the host load once, so a change to relay/supervisor.js, relay/session-host.js or relay/pty-bridge.py needs a stop and start by hand. A relay started with RELAY_WORKER=1 and no supervisor starts a host of its own, whose sessions end with it. If that host stops, that relay stops too, since nothing would start it again. The relay takes RELAY_KEY out of its own environment when it starts, so no git, gh or Claude Code it runs is given the key.

The demo. npm run office:demo plays three pretend sessions (office/demo-session.js), about two and a half minutes in all, with no Claude Code. DEMO_SPEED=2 plays it twice as fast. It starts its relay with RELAY_RESUME=0 and a sessions file of its own in a temporary folder, so it brings no session back and leaves your saved list alone. Without the relay, open office/ from any web server and press Run a demo.

A second room

A second room on the same computer is a second relay with its own port and its own state folder. Nothing else needs to change:

RELAY_URL=http://localhost:8790 RELAY_STATE_DIR=~/.office-world-b RELAY_KEY=another-key npm run office

npm run office starts the relay on the port in RELAY_URL. RELAY_STATE_DIR moves every state file to that folder: tickets, tasks, sessions, the Lead, the Lead's handoff notes and the rest (see Files on disk). Without it, both relays would use ~/.office-world, and the second would find the files owned by the first and keep its state in memory only. The session host is the relay's own, with its socket in a new folder each time it starts, so two relays never share one.

Each relay gives the sessions it starts its own address in OFFICE_HOOK_URL, with the session's token. The hook sends there first, so each room hears only its own sessions, even when the hooks in ~/.claude/settings.json were added for the other relay. Do not run npm run office:hooks for the second office: that replaces the hooks for the first. npm run office says so when it starts a second room, in place of the line that says how to add them. A session you start by hand in your own terminal still reports where those hooks say, which is the first room unless you change them.

The room's name. The sign on the back wall, the heading, the label at the top left of the scene and the page title show the room's name: company in office/roster.js, Building58 unless you change it. To tell two rooms apart side by side, add &name= to a page's address, for example http://localhost:8790/office/?channel=office&key=another-key&name=Room%20B. That page then shows Room B, and its title reads Room B · Building58. The name is cut to 40 characters, and a long one is drawn narrower so it fits on the sign. It changes only that page: the relay, the sessions and other pages keep company. Without name, or with an empty one, the page shows company.

The room bar

The bar under the page title holds what applies to the whole room, whichever session the panel shows. On the left, a chip each for Autopilot, the Lead and Reviews says what is on, and opens Settings at that section. On the right are Update (see Update, after a merge), Settings, and ?, which opens Roles and how work moves.

Notes about the whole room show once, under the bar: the warning about hooks from another checkout, a reviewer that posted and gave its desk back, sessions that could not come back, checkouts with nobody in them, the Lead's brief still waiting, and the offer to bring back the Lead's last session. Each goes away once it is dealt with.

The Claude Code panel

Type a folder in the Claude Code panel and press Add worker, once per session. The folder starts as the one the session on screen started from, or the relay's own folder when there are none. The relay runs claude (or CLAUDE_CMD) on your computer, with the room hooks for that session only (claude --settings), so you do not need to install anything. Where that session works is in Add worker's copy. To bring back an old conversation, put its id in Resume.

The panel needs python3 (it runs the terminal with Python's pty module, relay/pty-bridge.py) and claude on your PATH.

Only the room page on this computer can use it. The panel can run any command on your computer, so the relay only lets the room page itself use it: the request must come from this computer, to localhost or 127.0.0.1, from the relay's own page. A tunnel, another website or another computer gets 403, even with the key. The panel is off unless the relay starts with RELAY_TERMINAL=1. The Board, Tasks, checkouts and Update follow the same rule.

Clicking someone, in the scene or on the Floor list, shows their session in the terminal beside the room and replays the last 256 KB of it. Every session keeps running while you look at another, and reloading the page reconnects to all of them. Sessions the room starts get OFFICE_TERMINAL_ID, OFFICE_CHANNEL, OFFICE_PANEL_CHANNEL, OFFICE_TICKET_TOKEN, OFFICE_TICKET_URL and OFFICE_HOOK_URL, and RELAY_KEY is taken out of what they inherit.

Sessions from your own terminal

npm run office:hooks adds the room hooks to ~/.claude/settings.json, and keeps a copy of the old file as settings.json.before-office. OFFICE_RELAY_KEY=pick-a-key node relay/office-hook.js --settings prints them, to add by hand instead, and node relay/office-hook.js --uninstall takes them out. They report to channel office. To pick another channel, add --channel <name>: npm run office:hooks -- --channel my-project. OFFICE_CHANNEL works too, except the value the room gives a session it started: run inside such a session, npm run office:hooks leaves that page's channel out, so the hooks do not send every session from then on to that one page. npm run office prints the command with --channel when you open a channel other than office. A new Claude Code session then gets a developer, marked other terminal on the Floor list. You can watch but not type. The relay does not run these sessions, so the page seats them itself: each takes the first person the relay has given to nobody, the Lead's desk last. When the relay gives that person to a session of its own, the one from your terminal moves to another free person, or leaves if nobody is free. If the desks run out, the one quiet the longest makes room for a session you add here, and one that is idle for 30 minutes gives its desk back. The page keeps no seats, so after a reload a session from your terminal is seated again by its next hook, and may be someone else.

With these hooks installed, sessions started from the panel use them too, and the panel does not add its own, so no event is sent twice. The panel gives each session OFFICE_HOOK_URL, its relay's address for its page's channel, and the session's token, and the hook sends there first. So a session started from /office/?channel=my-project works at a desk in that room, on the relay that started it, whatever relay, key or channel the installed hooks name. The key the hooks were added with is used only by sessions you start by hand, so add them again if you change the relay's key. A different key is turned away with no message. They also run office-hook.js from the folder they were added from, so add them from the relay's own folder. If they come from another folder, the panel says so under Add worker (see the message).

The hook runs in the background ("async": true), gives up on the relay after one second and always exits 0, so it never slows Claude Code down. If the page is not open, it misses the events, but the relay still keeps the state of each session it runs, and a page that opens later seats those people from it. What it sends is in What the hook sends.

While the relay is down. When the relay does not answer, as during the restart after Update, the hook adds the event to hook-queue.jsonl in the room's state folder, and exits 0 as before. That is the folder in RELAY_STATE_DIR, which a session the room started gets from its relay, or ~/.office-world. So two rooms on one computer each keep their own queue. Each event carries the time the hook ran. When the relay starts, it takes its sessions back, then applies the queued events in the order they happened, then deletes the file. A hook that reaches a relay that is still taking its sessions back waits with them. A hook that gave up just as the relay started is applied when the next hook arrives, or 3 seconds after the start.

  • Never older over newer. The relay keeps the time of the last event it applied to each session, and saves it with the session. An event older than that changes nothing. So a queued Stop applies after the restart, but a queued prompt does not undo a Stop that came after it.
  • Only what the relay would have taken. A queued event keeps the address it was for, and a hash of the token or key it would have sent, never the token or key itself. The relay applies one only if it was for this relay's port, and its hash is this relay's key, or the token of a session this relay runs, for that session. It drops anything else, such as an event meant for another room, and says in its log how many it applied.
  • Limits. The hook adds to the queue only if the state folder is there, which it is once a room has run with it, so hooks installed with no room running keep nothing. The file holds what the hook would have sent (see What the hook sends), only you can read it, and the hook stops adding to it once it is 1 MB. The relay drops events more than an hour old. The time an event carries is when node started the hook, so two hooks that fire within a few milliseconds of each other can carry their times in the wrong order. A queued event changes the session's state, and the page gets it only if it is open then.

Copies of the repo, and branches

Each task and worker gets a separate working copy of the repo, which git calls a worktree and the room's messages call a checkout. They live in the repo's .worktrees folder, which is listed in its own .git/info/exclude, so nothing in the repo changes. The relay keeps the list in RELAY_CHECKOUTS_FILE for workers, reviewers and the PM, and on each task for tasks.

Where the PM reads. Ask the PM takes the branch of the folder you typed, checks it against the remote the way a task does, and makes a checkout on no branch at the commit a task would start from: the remote's latest commit when your branch is only behind, or else your local branch. The folder you typed keeps its branch, its commit and its files. The relay's log says when the PM reads your local branch and why: there is no remote, the branch is not pushed, the remote could not be reached, or the branch has commits the remote does not. A branch with no commits cannot be checked out, so then the PM works in the folder itself, and the log says that too. The checkout goes when the PM's session ends, unless the PM left files or commits in it, which then wait for Clean up. One whose session did not come back after a restart goes too.

Which branch work goes to, in this repo today

Work merges to main. A ticket a worker or the Lead files starts from main, and so does one the PM files when you ask them from a folder on main. Its brief says to open the PR against main, and to push with a plain git push, not quiet or piped. The old office and office-worker-sessions branches are far behind, so if a card shows either as its base, press Change base and type main before you start it.

Every brief names the base the task records, and says it wins over any other branch the ticket text names, unless you tell the worker otherwise in its session. The ticket text does not count as you telling it. The worker opens the PR against that base, and does not reset, rebase or switch its branch onto a different branch, though it may catch up with the base. Old ticket text that says to work from office-worker-sessions is left as it is, so the brief is what keeps the worker on main.

Which branch a ticket starts from

A ticket records its branch when filed, and the card shows it as base. For you, that is the branch of the folder you typed. The PM files against the branch of the folder you asked them from. Any other session, wherever it runs, files against the repo's default branch. That is the branch its origin remote names, if the repo has a local branch of that name. Otherwise it is a local main or master, or else the branch the main folder is on. A folder on no branch, or on a branch whose name a task cannot use, cannot file.

Until a ticket starts, in Triage or Ready, you can press Change base on its card and type another local branch (POST /tickets/{id}/base). A branch that is only on the remote is refused, so fetch and check it out first. The change is also refused while the ticket is starting, or when another open ticket has the same title on that branch. The brief then names the new branch for the PR. Once it has started, its base stays. Filing the same title from another branch makes a new ticket. Old tickets with no recorded base start from the branch the main folder has checked out, and count as the same ticket for that title on any branch.

When a task starts, it checks its base against the remote, and never changes your local branch:

  • If your branch is only behind, the task starts from the remote's commit, since that is what the PR goes against.
  • If your branch has commits the remote does not, the task keeps them, and the brief says the PR will show them.
  • If the base was never pushed, or the remote cannot be reached, the task starts from your branch, and the brief says so.
  • In a repo with no remote, the task starts from your branch, and the brief says nothing about it.

A task

Its copy is <repo>/.worktrees/<name> on branch task/<name>, and only committed work comes across. Tasks outlive a relay restart, and so do their workers, who come back in the same conversation. Clean up keeps the branch, and git refuses if there is uncommitted work. If the copy holds only files git ignores, such as .env or node_modules, the task names them and asks before deleting them: press Delete them too, or Keep and copy out what you want first. A file that turned up after the question is asked about too.

Add worker

In a git repo, each worker gets <repo>/.worktrees/worker-<id> on a new branch worker-<id>, from what the folder has checked out, and the folder itself does not change. Tick Use this folder to work in the folder instead. Outside a git repo a worker just starts in the folder.

A worker nobody ever pressed Enter for, with no files or commits in their copy, leaves nothing behind. Any other copy stays so its session can come back, and the room bar lists it with Clean up once nobody is in it. As for a task, the page names ignored files and asks before deleting them. A branch with new commits stays, a branch the worker was on stays, and an unused worker-<id> goes.

A reviewer's copy is in Automatic review.

Bringing a session back

The relay keeps a list of the running sessions in ~/.office-world/sessions.json (RELAY_SESSIONS_FILE), with what it knows of each: its title, task, role, PR, Lead and board permission, and what hooks last said. When it starts, it takes back or brings back each one on the list.

  • After a restart, such as Update's, each session is still running in the session host. The relay takes it back as it is: the same process, desk, conversation and ticket token, its output so far, and the state hooks last gave it, so a turn in progress goes on. The relay's log says Took back and still running. A hook sent in the second or two while no relay runs is lost, so a turn that ended then still shows as working until the next hook. A session still running that the relay does not take back, for example because its task is gone, ends.
  • After a stop, when Ctrl+C or the end of the supervisor ended the host and every session, their conversations are kept. The relay brings back each one with claude --resume, in the same folder, with the same title, task, role, PR, and Lead and board permission. They get new desks, and keep their session ids. A resumed session keeps the model it had. One that nobody spoke to has no conversation, so it starts a new one in the same place, on its role's model if one is set (Models and skills).

A task's worker comes back as Bring back would bring it. The Lead is not briefed again, unless its brief never went in. A session whose hooks never heard a turn, from a prompt, a tool or the end of a turn, has no conversation yet, so it starts a new one in the same folder. That covers Enter at the question about trusting the folder, a session just after /clear, and a new session with no hooks reaching the relay, even if you typed into it. A session after /compact keeps its conversation and comes back in it. A session you stopped yourself, or the Lead stopped, is not on the list and stays stopped, except the Lead. Then, if no Lead came back, the relay brings back the saved Lead, or starts a new one in its own folder (see the Lead when the relay starts). RELAY_LEAD=0 turns that off. To start with nobody, the Lead too, set RELAY_RESUME=0. A relay that starts no session leaves the saved list as it was.

A session that cannot come back, because claude --resume failed or it exited with an error within ten seconds, not from /exit, stays on the list marked failed, and so does its checkout, unless its folder is gone. One you quit yourself does not count. The room bar shows it as Could not come back with its id, and the next start tries again, up to three times. Resume on that line fills in the folder and the id, so Add worker tries now. For a task's worker the button is Bring back, which brings it back as the task, as the tasks list does. Forget takes it off the list (POST /terminals/failed).

Anything that did not come back can still be brought back by hand. Bring back does this for a task. For anything else, put the session's id in Resume and start it in the folder where it first ran, which for a worker with their own copy is that copy. Resume always stays in the folder you give it. With RELAY_LEAD=0, if the Lead's last session is not running after a restart, the panel offers to bring it back, and keeps the Lead's desk until you answer (see the Lead when the relay starts).

Update, after a merge

The relay runs the code in the folder it was started from, so a merge on GitHub changes nothing until that folder has it. Press Update in the room bar. It runs git fetch in that folder (RELAY_UPDATE_DIR) and plans from what came in. The folder itself changes only when Update moves it to the fetched commit with git merge --ff-only: at once for page changes, and just before the relay exits for relay changes. It refuses, and says why, if the folder is not on main, has changes to tracked files, or has commits its upstream does not, so it never merges or overwrites anything. relay/update.js and office/update.js do this.

  • Page changes only: the folder moves to the fetched commit, the page reloads, and nothing else stops.
  • Relay changes (files under relay/, tests aside): the relay waits until hooks say no session is in a turn, then moves the folder to the fetched commit and exits, and the supervisor starts it again from the new code, on the same port with the same key. The sessions keep running in the session host through the restart, the new relay takes each one back, and the page reloads once the relay answers. While it waits, the folder is as it was, so the running relay serves the old pages and the global hooks run the old office-hook.js. A merge Autopilot sees in that wait is fetched into the same update. The panel names who it is waiting for, and Call off the restart stops the wait and leaves the folder as it was. Relay files count from the commit the running relay started from, so after a git pull by hand, pressing Update offers the restart even when nothing is new. If a session starts a turn just as the restart begins, or the folder cannot fast-forward then, for example because a file was changed by hand, the restart is called off, the folder stays as it was, and the panel says so.
  • If the new relay fails, and RELAY_ROLLBACK=1 is on, Update goes back to the last commit that worked. See When the new relay fails.
  • If the relay does not come back within a minute, for example because the new code fails to start and the rollback is off, the panel stops saying Restarting and points you to the terminal where the relay runs. That terminal says why the supervisor stopped. The supervisor's stop ends the sessions too, and they are saved, so starting it by hand brings everyone back.
  • A change to relay/supervisor.js, the small process that restarts the relay, or to relay/session-host.js or relay/pty-bridge.py, which run the sessions, needs you to stop the relay and start it again once. The panel says so.

What the restart waits for. The restart cuts nothing off: every session runs on in the session host, and nothing can be typed into one while no relay runs. A hook sent in the second or two with no relay is not lost: it waits in the hook queue, and the new relay applies it once it has taken the sessions back. What it can lose is what lives only in the relay's memory. So it waits for these:

  • A session in a turn. If its turn ends in that gap, its Stop waits in the hook queue, and until the new relay applies it, the session counts as working, so nothing is typed into it.
  • Enter pressed in the last few seconds: a prompt you send yourself counts as a turn before its hook arrives.
  • A session you answered at a question, while it still prints. Its turn goes on, but no hook says so until its next tool or its end, so the relay still says it is at a question. Claude Code's spinner prints all through a turn, so once its screen has not moved for 5 seconds, as after Esc, it holds nothing. The panel names it as answered its question, so it is in a turn.
  • A first prompt the relay has typed but not yet sent with Enter. The panel names it as the relay is typing its first prompt.
  • Text left in a prompt, until you send or clear it. The new relay would not know it is there, and could type a message onto it.
  • A session you have spoken to that no hook has reached, since the relay cannot tell whether it is in a turn. A session just brought back with claude --resume is like this until its first hook.
  • A session running a job: out of its turn, but with a command it started still running, such as npm test in the background. The panel names it as running a job.
  • A checkout that Add worker or a PR review is still making.
  • A reviewer that has posted its review and is about to leave.
  • A refresh of the Lead, until it ends. The panel names it as The Lead (refreshing). It holds the restart even while the Lead is at a question, until the refresh ends or hits its 15 minute limit. While it runs, the relay still types into the Lead during the update, so its steps and the brief /clear brings go in. A message saved for the Lead can go in then too, as during any refresh. A refresh cannot start once an update is under way.
  • An open huddle, until its answer time ends (3 minutes by default). Its questions are not typed during the update, so a session not yet asked is not asked.

A session at a question or a permission prompt that nobody has answered does not hold the restart, however long it has been there. Only the relay types into it, so it is still at its question when the new relay takes it back, and you answer it there as before.

While an update is under way, the relay types no saved message into any session. Saved messages and huddle questions stay in their file and reach the sessions after the restart. That covers a task's brief and the Lead's brief too, which are saved with their session and typed after the restart. A first prompt for a reviewer, the PM or the COO is not held while the update waits for a quiet moment: that wait can last hours while Autopilot works, and a reviewer held all that time sits with no prompt. It is typed as soon as its session is ready, and the update then waits for its turn like any other. Only the restart itself holds it: one still waiting then, or typed with no turn begun yet, stays saved and goes in after the restart (A first prompt). A second press of Update while one is under way is refused.

The panel shows an update under way also when you did not press Update, such as Autopilot's pull after a merge: it looks every 10 seconds. While an update waits, Autopilot goes on, and stops only once the restart begins. When it merges a PR in that wait, it fetches main into the same update, so the restart pulls and runs the newest code. If the relay restarted between two of the panel's looks, the page reloads.

A session running a job holds the restart until its oldest job has run for RELAY_AUTOPILOT_STALL_MS (30 minutes, Give you a stuck task after in Settings). After that it holds nothing, so a command that never ends, such as a dev server, cannot hold the update for good. The restart does not end the job, since the session runs on in the session host.

When the new relay fails

A change that breaks the relay leaves every session with no relay to drive it, including the ones that could fix it. So the supervisor can check each relay it starts, and go back to the last commit that worked. It is off by default. Start the relay with RELAY_ROLLBACK=1 to turn it on, and without it to turn it off. relay/rollback.js does this, and the supervisor loads it once, so a broken relay cannot break it. Turning it on, or a new version of it, needs one stop and start by hand, like any change to the supervisor.

  • The check. Within RELAY_ROLLBACK_SECONDS (60) of each start, the relay must answer /health, serve the room page, and take back or bring back the sessions it saved. A session whose task or folder is gone does not count against it, and nor does one that already failed to come back on an earlier start, since that says nothing about the new code. One that comes back and then ends within seconds is not seen by the check. The check calls the relay at 127.0.0.1, or at localhost or ::1 when HOST is one of them. A relay bound only to another address never passes, so leave HOST at its default while the switch is on.
  • A pass records the commit of the relay's folder as the last good one, in ~/.office-world/good-commit.json (RELAY_GOOD_FILE), outside the repo, beside the relay's other state, with the folder it came from. A record from a relay in another folder, such as another checkout, is not used. The terminal says passed its check.
  • A fail after an Update's restart, from the button or from Autopilot's pull after a merge, stops the new relay if it still runs, so it saves its sessions, then checks out the recorded commit in the relay's folder, and starts the relay on it. The terminal says what failed and Rolled back to which commit. The page reloads when the relay is back, and the panel says which commit failed, why, and which commit runs now.
  • The folder is then on that commit, not on main, so Update pulls nothing more, and says so, until you fix main and check it out there yourself. Autopilot's pulls are refused the same way. Once a branch is checked out there, the panel stops saying the relay rolled back.
  • Once in a row. If the relay on the old commit fails its check too, it does not roll back again. It keeps running if it can, and the terminal says why.
  • Never over your changes. If the folder has changes to tracked files, it does not roll back, and the terminal names the files. A file git does not track stops it only if git would overwrite it. Then git refuses, the folder stays as it was, and the relay starts again on the same new code, which does not roll back again.
  • Back to code from before the session host. The supervisor keeps the host and its sessions running through a rollback. A relay from a commit before the host existed does not use it, so it starts each saved session again with claude --resume, and each conversation runs in two processes until you stop the relay and start it again. Do that after such a rollback.
  • A fail on a start you make by hand, or before any commit has passed, does not roll back: there is nothing to go back from, or to.

The five questions of article 5, for this switch:

  1. What starts it? The supervisor, each time it starts the relay, while RELAY_ROLLBACK=1. It rolls back only on a start that followed an Update's restart.
  2. What does it read and write? It reads /health with the key, the room page, and the relay's folder with git. It writes good-commit.json, and checks out one commit in the relay's folder.
  3. What does it start next? The relay, once, on the old commit. That relay takes the sessions back, as any restart does.
  4. Where does the person come back in? The panel's note and the terminal after a rollback, and fixing main and checking it out, which Update waits for.
  5. What stops two sessions from doing the same work? There is one supervisor for each relay, and it rolls back at most once in a row.

Without the button, run git pull in that folder, then reload the page, or stop and start the relay for relay changes. Sessions come back either way. GET /update and POST /update are in the routes.

Keeping tickets in GitHub issues

Tickets are kept by a store, relay/ticket-stores/local.js by default, in RELAY_TICKETS_FILE. To replace it, write a module with the same five members, described at the top of that file, and start the relay with RELAY_TICKET_STORE=/path/to/store.js. Your store has to pass relay/test/ticket-store-contract.js. The rules stay in relay/tickets.js, and checkouts and workers stay in relay/tasks.js.

relay/ticket-stores/github.js keeps tickets as GitHub issues. It is a pilot, and it is off unless you turn it on. To turn it on, log in with gh auth login, then start the relay with:

RELAY_TICKET_STORE=relay/ticket-stores/github.js RELAY_TICKET_REPO=owner/repo npm run office

RELAY_TICKET_REPO=owner/repo gives the office channel that repo. To give other channels a repo, use office=owner/repo,demo=owner/other. A channel with no repo has no tickets. Two channels cannot name the same repo, and the relay will not start if they do: a task belongs to one channel, so the other channel would offer Start again on its ticket.

The store calls GitHub with gh api, so it uses your gh login and needs no new key. This gives the relay write access to the repo's issues and labels through that login, which needs the repo scope for a private repo: it opens, edits, labels and closes issues, makes labels, and adds and removes issue dependencies.

What the Board shows maps to GitHub like this:

TicketOn GitHub
IdThe issue number.
Title, bodyThe issue's title and body. The repo, base and who filed it are in a hidden note at the end of the body, which the relay signs.
Triage, Ready, StartedThe labels office:triage, office:ready and office:started. The store makes them the first time it needs them.
DoneClosed as completed.
RejectedClosed as not planned.
PriorityThe label office:priority-high, office:priority-normal or office:priority-low.
Blocked byThe issue's dependencies.

An issue is a ticket only if it has an office: label, in any case. On GitHub, labels are added by people with triage or write access, and also by issue templates and Actions if the repo has them. The author of an issue, and anyone with write access, can edit its text, and a ticket's text becomes a worker's brief. Use a repo where you trust everyone who can do that.

A title or body edited on GitHub is cut to the limits a ticket filed in the room has: 80 and 8000 characters.

The relay signs the hidden note together with the issue number, and reads the note only when the signature holds. So a forged note, an edited one or one copied onto another issue is not read. The key is in ~/.office-world/github-store.key (RELAY_TICKET_KEY_FILE), made the first time it is needed. The key belongs to one computer:

  • A ticket filed on GitHub, or one whose note does not check, works in RELAY_TICKET_FOLDER (by default the repo folder that holds the relay's own code), starts from that folder's branch, and shows its GitHub author as who filed it.
  • When the relay changes a ticket whose note does not check, it keeps that note as it is and logs it. It refuses to change what only the note holds, such as the base. So if the key is lost or changed, the right key reads the tickets again.
  • Do not run a second relay, on another computer or with another key file, on the same repo. Each one would see the other's tickets as filed on GitHub, and could not change their base.
  • A ticket filed on GitHub has no note, so the first time the relay changes it, the relay signs its folder into a new note.

Filing opens the issue with no label, then adds the dependencies, the labels and the note. If a step after the first fails, the relay closes the issue as not planned, so it is not a ticket and a retry does not leave two open. If that close fails too, an unlabeled open issue is left, and you can close it by hand.

Other things to know:

  • The store needs a gh recent enough to have gh api --slurp, which arrived in 2024. Check gh api --help.
  • The hidden note puts folder paths from this computer into the issue bodies.
  • A pull request that says "Fixes #12" closes issue 12 as completed, so the Board shows it Done.
  • A blocker in another repo is not shown on the ticket, so the ticket does not wait for it.
  • Tickets on the local store do not carry over. Their ids, such as T-21, are not issue numbers.
  • A ticket you file on GitHub has no approval, so a Lead you let start tickets leaves it for you (see The Lead starts tickets).

The Board lists the issues once, then uses that list for RELAY_TICKET_CACHE_MS. After that it shows the old list at once and fetches a new one, so a change made on GitHub shows one refresh later. What the relay changes shows at once.
